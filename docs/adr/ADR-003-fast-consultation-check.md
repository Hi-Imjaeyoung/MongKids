# ADR-003: 관리자가 새 상담 신청을 빠르게 확인하는 방식

- **상태:** Accepted
- **날짜:** 2026-10-26
- **결정 책임자:** 저장소 관리자 (사용자)
- **관련 항목:** FR-005, FR-004, FR-026, FR-023, SCR-014 / 이슈 #46, #43
- **대체 관계:** 없음

## 1. 배경 및 문제

상담 신청(FR-001 기관, FR-002 개인)은 비회원도 할 수 있습니다. 신청은 DB에 저장만 되고 누구에게도 알리지 않습니다. 관리자가 새 신청이 들어온 것을 알려면 관리자 화면(SCR-014)의 상담 신청 메뉴를 직접 열어 봐야 합니다. 상담 신청은 이 서비스의 핵심 전환 지점이라, 확인이 늦으면 연락도 그만큼 늦어집니다.

원하는 결과는 다음과 같습니다.

1. 새 상담 신청이 들어오면 관리자가 오래 기다리지 않고 알아차린다.
2. 알아차린 뒤 신청 내용을 확인하고 연락하는 데까지 막힘이 없다.
3. 알림이 실패해도 신청 자체는 항상 저장된다.

FR-005는 처음에 "상담 신청 저장 시 입력된 전체 내용을 메일로 발송"으로 확정되었습니다(2026-10-14). 사용자 결정(2026-10-26)으로 "지금은 메일이 아닌 방식으로 관리자에게 알림"으로 바뀌었고, 구체적인 방식은 이 ADR에서 정합니다.

## 2. 요구사항 및 제약 조건

### 확인된 사실
- 상담 저장은 `ConsultationService.createInstitutionConsultation`과 `createPersonalConsultation`이 맡는다. 두 메서드는 `@Transactional`로 저장한 뒤 바로 끝나며, 저장 후 다른 동작은 없다.
- 백엔드에는 비동기 처리(`@Async`), 스케줄러(`@Scheduled`), WebSocket·SSE, 메일 관련 의존성이 없다.
- 프론트에는 서비스 워커와 웹 앱 manifest가 없다. 즉 PWA가 아니다.
- 관리자 화면은 `/admin`이다. 상담 신청은 처리 상태(`RECEIVED` 신규 / `CONTACTED` 연락 완료 / `COMPLETED` 상담 완료)로 거를 수 있다(FR-026, #43). 따라서 "아직 처리하지 않은 신청"은 `RECEIVED` 건으로 판별할 수 있다.
- 관리자는 헤더 이름 옆의 "관리자" 링크로 들어온다. 권한은 `MemberService.validateAdmin`이 DB의 현재 역할로 검사한다.
- `Member`에는 `email`·`phone` 필드가 있다. 소셜 로그인과 가입 정보에서 받는 값이며, 가입 정보 입력(FR-019)은 아직 구현되지 않았다.
- 개인 상담 신청에는 아이 이름, 주소, 건강·알레르기 메모(건강정보, 별도 동의)가 들어 있다(FR-002, FR-023).
- 카카오톡 채널, 공식 연락처, 사업자 정보는 대표 확인을 기다리고 있다(`docs/progress.md`).
- 백엔드는 운영 EC2 한 대에서 돈다. 비밀값은 Parameter Store에 둔다.

### 가정 및 가설
- 상담 신청 API는 로그인 없이 호출된다(FR-003). `SecurityConfig`에서 관리자 경로 외에는 `permitAll`이고, 신청 횟수 제한이나 봇 방지(캡차 등)는 없다.
- 가정: 상담 신청 건수는 많지 않다. 측정한 적이 없으므로 수치는 쓰지 않는다.
- 가정: 관리자(대표)는 주로 휴대폰으로 확인하며, 사이트를 계속 열어 두지는 않는다. 확인하지 않았다.
- 미정: "빠르게"의 목표 시간(몇 분 안인지, 업무 시간 안인지, 하루 안인지)이 정해지지 않았다. 대안 선택에 가장 큰 영향을 준다.
- 가설: 사이트 밖으로 알림을 보내는 방식(대안 C~G)은 관리자 기기나 외부 계정의 설정 상태에 따라 알림이 오지 않을 수 있다. 사이트 안 표시(대안 B)를 함께 두면 놓친 알림을 보완할 수 있다.

### 제약 조건 / 비목표
- 알림 발송 실패가 신청 저장이나 신청자 응답(201)에 영향을 주면 안 된다.
- 신청자에게 보내는 접수 확인 알림은 범위가 아니다.
- 강사 지원(FR-007) 알림은 이번에 다루지 않는다. 다만 선택한 방식을 나중에 재사용할 수 있으면 좋다.
- 메일은 사용자 결정(2026-10-26)으로 지금은 쓰지 않는다. 기록을 위해 대안 G로만 남긴다.

## 3. 결정 요인

- **신청 저장 보장 (절대 제약):** 알림은 저장 트랜잭션이 커밋된 뒤에 보내고, 실패해도 신청 응답은 성공해야 한다.
- **즉시성:** 관리자가 사이트를 열지 않았을 때도 알 수 있는지. 목표 시간이 정해지면 제약이 되고, 그전까지는 가장 무거운 선호 사항이다.
- **개인정보 (조건부 제약):** 알림 내용에 이름·전화번호·건강 메모가 들어가면 외부 서비스에 개인정보가 남는다(FR-023). 외부 채널을 쓴다면 본문을 최소화하는 것이 제약이 된다.
- **외부 의존과 운영 비용:** 사업자 등록, 채널·템플릿 심사, 발신 번호 등록, 건당 요금, 관리할 비밀값이 얼마나 늘어나는지. 선호 사항이다.
- **구현 복잡도:** 비동기 처리, 서비스 워커, 기기 구독 관리 등 새로 들어오는 구성이 얼마나 되는지. MVP 마감(2026-11-11)을 고려한 선호 사항이다.
- **신뢰성:** 알림이 오지 않았을 때 관리자가 알아챌 수 있는지, 놓친 신청을 다시 찾을 수 있는지.

## 4. 검토한 대안

### 대안 A — 현상 유지 (관리자 화면을 직접 확인)
- **접근 방식:** 추가 개발 없이 관리자가 `/admin?tab=consultations`에서 신규 필터로 확인한다.
- **장점:** 비용과 위험이 없다. 개인정보가 외부로 나가지 않는다.
- **비용 및 위험:** 관리자가 들어오기 전까지는 아무도 알 수 없다. 1절의 원하는 결과 1을 충족하지 못한다.
- **적합한 경우:** 신청이 드물고, 관리자가 하루에 한두 번 관리자 화면을 확인하는 습관이 있을 때.

### 대안 B — 사이트 안 신규 건수 표시
- **접근 방식:** 신규(`RECEIVED`) 건수를 돌려주는 관리자 API를 둔다. 헤더의 "관리자" 링크와 상담 신청 메뉴에 건수 배지를 표시하고, 관리자가 로그인해 있는 동안 주기적으로 다시 조회한다(폴링).
- **장점:** 외부 의존과 비용이 없다. 기존 관리자 API·권한 검사·처리 상태(FR-026)를 그대로 쓴다. 개인정보가 밖으로 나가지 않는다. 신청을 처리하면 배지가 줄어들어, 놓친 신청이 남지 않는다.
- **비용 및 위험:** 관리자가 사이트를 열지 않으면 알 수 없다. 즉시성 요인은 충족하지 못한다. 폴링 주기만큼 요청이 늘어나지만, 관리자 한두 명이라 무시할 만한 수준으로 예상된다(추정).
- **적합한 경우:** 관리자가 사이트를 자주 연다. 또는 외부 알림과 함께 "놓친 건 보완" 용도로 쓸 때.

### 대안 C — 웹 푸시 (Web Push)
- **접근 방식:** 프론트에 서비스 워커를 추가한다. 관리자가 알림 권한을 허용하면 구독 정보를 서버에 저장한다. 신청이 저장되면 서버가 VAPID 키로 푸시를 보낸다.
- **장점:** 사이트를 닫아도 기기 알림으로 온다. 외부 유료 서비스나 심사가 없다. 푸시 본문은 우리가 정하므로 최소화(예: "새 상담 신청 1건")하기 쉽다.
- **비용 및 위험:** 서비스 워커, 구독 저장 테이블(DDL), 푸시 라이브러리 의존성, VAPID 키 관리가 새로 필요하다. 기기·브라우저마다 따로 구독해야 하고, 권한을 거부하거나 브라우저 데이터를 지우면 알림이 끊긴다. iOS는 홈 화면에 추가한 웹 앱에서만 웹 푸시를 받는다고 알려져 있다(외부 문서 기준, 확인 필요). 구현량은 대안 중 큰 편이다.
- **적합한 경우:** 외부 서비스 없이 휴대폰 즉시 알림이 필요하고, 관리자 기기 설정을 한 번 도와줄 수 있을 때.

### 대안 D — 카카오 알림톡
- **접근 방식:** 카카오톡 비즈니스 채널과 발송 대행사(딜러사)를 통해, 심사를 거친 템플릿으로 관리자 휴대폰에 알림톡을 보낸다.
- **장점:** 국내 사용자에게 가장 익숙하고 도달률이 높을 것으로 예상된다(가정). 관리자가 앱을 따로 설치할 필요가 없다.
- **비용 및 위험:** 비즈니스 채널(사업자 정보 필요)과 대행사 계약, 템플릿 심사가 선행되어야 한다. 카카오 채널은 아직 대표 확인 전이다. 건당 요금이 든다(금액은 대행사 요금표 확인 필요). 대행사 API 키를 관리해야 하고, 메시지에 개인정보를 넣으면 외부에 남는다.
- **적합한 경우:** 카카오 채널과 사업자 정보가 확정되어 있고, 나중에 신청자 접수 확인 알림까지 확장할 계획이 있을 때.

### 대안 E — 문자(SMS)
- **접근 방식:** 문자 발송 서비스(국내 대행사 또는 클라우드 메시징)로 관리자 번호에 문자를 보낸다.
- **장점:** 모든 휴대폰에서 받는다. 앱이나 브라우저 설정이 필요 없다.
- **비용 및 위험:** 국내 발송은 발신 번호 사전 등록(번호 소유 인증)이 필요하다. 건당 요금이 든다(금액은 요금표 확인 필요). API 키를 관리해야 하고, 본문에 개인정보를 넣으면 외부에 남는다.
- **적합한 경우:** 공식 연락처(발신 번호)가 확정되어 있고, 설치 없이 확실한 도달이 가장 중요할 때.

### 대안 F — 메신저 봇 웹훅 (텔레그램, 디스코드, 슬랙 등)
- **접근 방식:** 관리자가 쓰는 메신저에 봇이나 수신 웹훅을 만들고, 신청이 저장되면 서버가 HTTP 요청 한 번으로 메시지를 보낸다.
- **장점:** 보통 무료이고 구현이 가장 단순하다(HTTP 호출 하나와 비밀값 하나). 휴대폰 앱 알림으로 바로 온다. 여러 사람이 같은 방에서 받을 수 있다.
- **비용 및 위험:** 관리자가 해당 메신저를 설치하고 써야 한다. 메시지가 제3자 서비스에 남으므로, 본문은 유형과 관리자 화면 링크 정도로 최소화해야 한다(FR-023). 웹훅 주소나 봇 토큰이 유출되면 누구나 그 방에 메시지를 보낼 수 있다(Parameter Store SecureString으로 관리). 서비스 약관이나 API가 바뀔 위험이 있다.
- **적합한 경우:** 빠르게 즉시 알림이 필요하고, 관리자가 쓰는 메신저가 정해져 있을 때.

### 대안 G — 메일 (기존 FR-005 방식, 보류)
- **접근 방식:** AWS SES 등으로 관리자 메일에 신청 내용을 보낸다.
- **장점:** 기록이 메일함에 남고, 대부분 무료 사용량 안에서 쓸 수 있을 것으로 예상된다(추정, 요금 페이지 확인 필요).
- **비용 및 위험:** 도메인 인증, SES 샌드박스 해제, IAM 권한이 필요하다. 메일 확인 습관에 따라 즉시성이 달라진다. 원래 요구대로 전체 내용을 보내면 건강정보가 메일함에 남는다.
- **적합한 경우:** 사용자 결정(2026-10-26)으로 지금은 쓰지 않는다. 기록이나 보관 목적이 생기면 다시 검토한다.

### 권장 검토 (결정 아님)
대안 B(사이트 안 신규 건수)는 외부 의존 없이 놓친 신청을 보완합니다. 여기에 사이트 밖 알림 하나(C, D, E, F 중)를 조합하는 방식을 우선 검토하는 것을 제안합니다. 사이트 밖 알림은 1절의 미정 사항인 목표 시간과, 관리자가 실제로 쓰는 채널이 정해져야 고를 수 있습니다.

## 5. 결정

- **선택한 대안:** 대안 B — 사이트 안 신규 건수 표시 (사용자 결정 2026-10-26)
- **근거:**
  - 상담 신청에는 인증이 없습니다(FR-003). 횟수 제한과 봇 방지도 없습니다. 그래서 신청이 들어올 때마다 사이트 밖으로 알림을 보내면(C~G), 누군가 신청을 반복해 넣을 때 그만큼 관리자 기기에 알림이 쏟아집니다. 건당 요금이 드는 채널이라면 비용도 함께 늘어납니다. B는 신청마다 무언가를 보내지 않고 처리되지 않은 건수만 보여 주므로, 신청이 몰려도 관리자가 받는 알림 부하가 늘지 않습니다.
  - MVP 마감(2026-11-11) 전에 외부 의존 없이 기존 관리자 API, 권한 검사, 처리 상태(FR-026)만으로 만들 수 있는 최소 기능 단위입니다. 사이트 밖 알림은 이후에 리팩토링하면서 더합니다.
  - 알림을 보내는 동작이 없으므로 "알림 실패가 신청 저장에 영향을 주면 안 된다"는 절대 제약을 자연히 만족합니다. 외부로 개인정보가 나가지도 않습니다.
- **다른 대안을 선택하지 않은 이유:**
  - A 현상 유지: 관리자 화면에 들어가 신규 필터를 걸기 전에는 새 신청이 있는지 알 수 없습니다.
  - C 웹 푸시, D 알림톡, E 문자, F 메신저 웹훅: 인증 없는 신청이 그대로 알림 횟수가 됩니다. 신청 제한이나 묶어 보내기 같은 부하 대책이 먼저 필요합니다. D와 E는 사업자 정보, 채널, 발신 번호 같은 선행 조건도 아직 갖춰지지 않았습니다.
  - G 메일: 사용자 결정(2026-10-26)으로 보류했습니다.

## 6. 결과

### 기대 효과
- 관리자가 사이트에 들어오면 헤더와 상담 신청 메뉴에서 처리하지 않은 신청이 몇 건인지 바로 봅니다.
- 신청을 처리(연락 완료, 상담 완료)하면 건수가 줄어들어, 놓친 신청이 화면에 계속 남습니다.
- 외부 서비스, 새 비밀값, 새 운영 설정이 없습니다.

### 감수하는 트레이드오프 / 위험
- 관리자가 사이트를 열지 않으면 알 수 없습니다. "빠르게"의 목표 시간을 정하지 않은 채, 즉시성을 일부 포기합니다.
- 관리자가 로그인한 동안 폴링 요청이 늘어납니다. 관리자 수가 적어 부담은 작을 것으로 예상됩니다(추정, 측정 전).
- 인증 없는 신청이 몰리는 문제 자체를 막지는 않습니다. 건수가 비정상적으로 늘어나는 것을 관리자가 화면에서 볼 수 있을 뿐입니다.

### 후속 작업
- FR-005를 "관리자 화면의 신규(RECEIVED) 상담 건수 표시"로 갱신합니다.
- 백엔드: 신규 건수를 돌려주는 관리자 API를 만듭니다(`/api/v1/admin/...`, `validateAdmin`, 기존 처리 상태 인덱스 활용).
- 프론트: 관리자일 때 헤더 "관리자" 링크(모바일 메뉴 포함)와 상담 신청 메뉴에 건수 배지를 붙입니다. 폴링 주기와 화면 포커스 시 다시 조회할지는 구현할 때 정합니다. 처리 상태를 바꾸면 건수를 바로 반영합니다.
- 사이트 밖 알림으로 리팩토링하기 전에, 상담 신청 횟수 제한이나 봇 방지 같은 부하 대책을 따로 검토합니다.

## 7. 검증 계획

- 테스트: 관리자는 신규 건수를 200으로 받습니다. 직원·일반 회원은 403, 비로그인은 401을 받습니다. 신청을 저장하면 건수가 늘고, 처리 상태를 바꾸면 줄어듭니다.
- 로컬 QA: 신청을 넣은 뒤 관리자 화면에서 배지가 폴링 주기 안에 갱신되는지, 처리하면 줄어드는지 확인합니다.
- 운영 초기 몇 주 동안, 관리자가 신청을 늦게 알게 된 일이 있었는지 확인합니다. 그 결과를 사이트 밖 알림 도입 여부의 근거로 씁니다.

## 8. 재검토 조건

- 관리자가 신청을 늦게 확인해 연락이 늦어지는 일이 생길 때. 또는 "빠르게"의 목표 시간이 정해져 사이트 안 표시로는 부족할 때.
- 상담 신청에 횟수 제한, 봇 방지 같은 부하 대책이 생겨, 사이트 밖 알림(C~F)의 알림 폭주 위험이 줄었을 때.
- 카카오 채널과 사업자 정보가 확정되어 알림톡을 쓸 수 있게 될 때.
- 신청 기록이나 보관 목적으로 메일(대안 G)이 다시 필요해질 때.
- 신청자 접수 확인 알림이나 강사 지원(FR-007) 알림처럼 같은 채널을 쓸 요구가 생길 때.

## 9. 이력

- 2026-10-26 — Proposed — 초안 작성. FR-005를 메일 발송에서 상담 접수 알림으로 재정의(사용자 결정)한 데 따라, 알림 방식을 문제 중심으로 검토.
- 2026-10-26 — Accepted — 대안 B(사이트 안 신규 건수 표시) 선택. 근거: 인증 없는 상담 신청에서 생길 수 있는 알림 부하를 피하고, 최소 기능으로 먼저 구현한 뒤 사이트 밖 알림은 나중에 리팩토링.
