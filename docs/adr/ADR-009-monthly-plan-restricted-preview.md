# ADR-009: 월간 수업 계획안의 비인증 미리보기 제공 방식

- **상태:** Accepted
- **날짜:** 2026-11-19
- **결정 책임자:** Hi-ImJeaYoung
- **관련 항목:** [requirement_homepage.md](../requirements/requirement_homepage.md) SCR-027, FR-032, 미결 사항 "수업 계획안", [ADR-002](ADR-002-s3-orphan-photo-cleanup.md)(S3 파일 정리), `front/src/components/plan/PlanViewer.jsx`, 구현 이슈 #107
- **대체 관계:** 없음

## 1. 배경 및 문제

수업 계획안 화면(SCR-027)은 연간 계획안은 누구나, 주차별 상세가 담긴 월간 계획안은 인증된 사람만 보게 한다(FR-032). 비인증 방문자에게도 월간 계획안이 "있다"는 것은 보여 주되(블러 미리보기), 내용은 읽을 수 없어야 한다.

정해야 할 것은 이 미리보기를 무엇으로 만들고, 원본을 어떻게 비인증 방문자에게서 떼어 놓을지다. 원하는 결과는 다음과 같다.
- 비인증 방문자가 브라우저 개발자 도구나 URL 직접 접근으로도 월간 계획안 원본을 얻을 수 없다.
- 관리자(대표)가 계획안을 올리는 일이 번거롭지 않다.
- 미리보기가 원본과 어긋나지 않는다(다른 달 원본에 엉뚱한 미리보기가 붙지 않는다).

## 2. 요구사항 및 제약 조건

### 확인된 사실
- FR-032: 월간 계획안은 인증된 사람에게만 반환하며 "화면에서만 가리지 않고 서버가 거른다"(사용자 결정 2026-11-19).
- SCR-027: 비인증에게는 블러 처리한 이미지를, 원본 PDF는 인증된 사람에게만 제공(사용자 결정 2026-11-19). PDF는 이미지로 바꿔 화면 안에서만 보여 주고 내려받기·인쇄는 없음(초안 가정).
- 미결 사항: 등록 형식은 "연간 이미지, 월간 블러 이미지 + 원본 PDF 두 가지로 받는 방식"이 2026-11-19 사용자 결정으로 기록되어 있다. 이 ADR은 그 방식을 다시 검토하는 근거가 된다.
- 인증 방법(고유번호증·사업자등록증 확인 등)은 아직 미결이다. 이 ADR의 범위가 아니다.
- 현재 프론트 `PlanViewer.jsx`는 월간이면 `plan.preview`(별도 미리보기 이미지)를, 연간이면 `plan.image`를 쓴다. 데이터는 정적이고 FR-032 API는 아직 없다.
- 백엔드 `S3FileStorage.getUrl`은 `publicBaseUrl + key`로 공개 URL을 만든다. 사진은 이 URL로 CloudFront(OAC)를 거쳐 누구나 읽을 수 있다(`docs/deploy-checklist.md`). 업로드는 presigned PUT이다.
- 화면에서 이미지 저장 메뉴·끌어 놓기는 막지만 화면 캡처는 막을 수 없다(`PlanViewer.jsx` 주석).

### 가정 및 가설
- 가정: 월간 계획안은 매달 몇 건 수준이며 관리자 한 명이 올린다. 건수는 확인하지 않았다.
- 가정: 원본은 PDF 한 파일이며 여러 쪽일 수 있다.
- 가설: CSS `filter: blur()`처럼 브라우저에서 흐리게 하는 방식은 원본 파일 자체가 브라우저로 내려가므로, 네트워크 탭·이미지 URL로 원본을 얻을 수 있다.
- 가설: 서버에서 PDF를 이미지로 렌더링하면, 글꼴이 포함되지 않은 한글 PDF는 글자가 깨질 수 있다. 실제 계획안 PDF로 확인하지 않았다.

### 제약 조건 / 비목표
- 화면 캡처·사진 촬영 방지는 목표가 아니다(어떤 대안으로도 막을 수 없다).
- 인증 방법 결정, 인증된 사람의 원본 보기 화면(PDF 뷰어 방식)은 범위 밖이다.
- 새 의존성(예: PDF 렌더링 라이브러리)은 사용자 확인 후 추가한다(저장소 공통 규칙).

## 3. 결정 요인

- **보안(절대 제약):** 비인증 응답·공개 URL 어디에도 원본이나 원본을 복원할 수 있는 데이터가 없어야 한다. FR-032 "서버가 거름"에서 나온 조건이다.
- **관리자 운영 부담(중요):** 매달 올릴 때 해야 할 일이 적고, 실수(미리보기와 원본 불일치, 블러 안 된 이미지 업로드)의 여지가 적어야 한다.
- **개발 기간과 복잡도(중요):** 새 의존성·서버 이미지 처리 없이 기존 S3 업로드 흐름을 재사용할 수 있으면 좋다.
- **데이터 무결성(선호):** 미리보기와 원본이 같은 계획안에 묶여 함께 바뀌고 함께 지워져야 한다(ADR-002의 고아 파일 정리와 연결).

## 4. 검토한 대안

### 대안 A — 미리보기와 원본을 서로 다른 파일로 등록 (관리자가 둘 다 올림)
- **접근 방식:** 관리자가 월간 계획안마다 블러 처리한 미리보기 이미지와 원본 PDF를 각각 올린다. 미리보기는 공개 경로(기존 사진 CloudFront)에, 원본은 공개 CloudFront가 읽지 않는 비공개 위치에 둔다. API는 비인증에게 미리보기 URL만 주고, 인증된 사람에게만 원본 접근(짧은 만료 presigned GET 또는 API 경유 전달)을 준다.
- **장점:** 비인증 응답에 원본이 아예 없으므로 보안 조건을 확실히 만족한다. 서버 이미지 처리·새 의존성이 없다. 현재 프론트(`plan.preview`/`plan.image` 분리)와 2026-11-19 사용자 결정에 그대로 맞는다. 미리보기에 무엇을 보여 줄지(1쪽만, 일부만) 관리자가 고를 수 있다.
- **비용 및 위험:** 관리자가 매번 블러 이미지를 직접 만들어야 한다(편집 도구 필요). 블러가 약한 이미지를 올리면 내용이 노출된다. 미리보기와 원본이 다른 달 것으로 짝지어질 수 있다. 업로드 두 번, 파일 정리 대상도 두 개.
- **적합한 경우:** 등록 건수가 적고 관리자가 이미지 편집에 익숙할 때, 또는 빨리 출시해야 할 때.

### 대안 B — 원본 하나만 등록하고 화면(브라우저)에서 블러 처리
- **접근 방식:** 관리자는 원본 PDF(또는 원본 이미지) 하나만 올린다. 비인증 방문자에게도 같은 파일을 내려 주고 프론트가 CSS 블러와 잠김 안내를 덮는다.
- **장점:** 관리자 부담이 가장 적다. 미리보기·원본 불일치가 생기지 않는다. 구현이 가장 단순하다.
- **비용 및 위험:** 원본이 브라우저로 내려가므로 개발자 도구, 이미지 URL 열기, CSS 끄기로 누구나 원본을 볼 수 있다. FR-032의 "화면에서만 가리지 않고 서버가 거름"과 정면으로 충돌한다. 원본 URL이 공개되면 검색·공유로 퍼질 수 있다.
- **적합한 경우:** 월간 계획안이 실제로는 비밀이 아니고 "인증 유도" 연출만 필요할 때. 이 경우 FR-032를 먼저 바꿔야 한다.

### 대안 C — 원본 하나만 등록하고 서버가 블러 미리보기를 만들어 따로 저장
- **접근 방식:** 관리자는 원본 PDF 하나만 올린다. 서버가 업로드 확인 시 첫 쪽(또는 정한 쪽)을 이미지로 렌더링해 강하게 블러·축소한 미리보기를 만들어 공개 경로에 저장하고, 원본은 대안 A처럼 비공개로 둔다. 비인증 응답은 대안 A와 같다.
- **장점:** 보안 조건은 대안 A와 같다(비인증에게는 서버가 만든 미리보기만). 관리자는 한 번만 올리고, 블러 강도가 서버에서 일정하게 보장되며, 미리보기와 원본이 항상 짝이 맞는다.
- **비용 및 위험:** PDF 렌더링 라이브러리(예: Apache PDFBox) 추가가 필요하다. 업로드가 presigned PUT으로 S3에 바로 가므로, 서버가 S3에서 원본을 다시 읽어 처리하는 단계가 생긴다. 한글 글꼴 미포함 PDF의 렌더링 품질은 확인 전(가설). 큰 PDF 처리 시 메모리·시간 부담은 측정 전.
- **적합한 경우:** 매달 꾸준히 올리고 관리자 실수를 줄이는 것이 중요할 때, 또는 대안 A로 운영하다 관리자 부담이 문제로 드러났을 때.

### 대안 D — 현상 유지: 미리보기 없이 잠김 안내만 표시
- **접근 방식:** 월간 계획안은 제목·기간과 잠김 안내만 보여 주고, 미리보기 이미지는 두지 않는다. 원본은 대안 A처럼 비공개.
- **장점:** 보안 조건을 만족하고 관리자는 원본만 올린다. 추가 구현이 가장 적다.
- **비용 및 위험:** SCR-027의 "비인증에게 블러 이미지를 보여 줌" 결정과 맞지 않는다. 계획안이 실제로 있다는 느낌이 약해 인증 유도 효과가 떨어질 수 있다(측정 안 됨).
- **적합한 경우:** 인증 방법이 정해지기 전 임시 단계, 또는 미리보기 효과가 크지 않다고 판단될 때.

### 공통 사항 (대안 A·C·D)
- 원본은 현재 사진용 공개 CloudFront 경로(`getUrl`)로 내보내면 안 된다. 비공개 키 접두사 또는 별도 버킷에 두고, 인증 확인 후에만 짧은 만료 URL이나 API 응답으로 준다. 세부 방식은 구현 시 정한다.

## 5. 결정

- **선택한 대안:** 대안 A — 미리보기(블러 이미지)와 원본 PDF를 서로 다른 파일로 등록.
- **근거:** 미리보기에서 어느 영역을 블러할지(어디까지 보여 주고 어디를 가릴지)를 계획안마다 관리자가 직접 골라야 한다(사용자 결정 2026-11-19). 대안 A는 관리자가 만든 미리보기를 그대로 쓰므로 이 조건을 만족하고, 비인증 응답에 원본이 없어 보안 조건(FR-032)도 만족한다. 서버 이미지 처리·새 의존성이 없고 현재 프론트 구조(`plan.preview`/`plan.image`)와도 맞는다.
- **다른 대안을 선택하지 않은 이유:**
  - 대안 B: 원본이 브라우저로 전달되어 FR-032(서버가 거름)를 어긴다.
  - 대안 C: 서버가 일정한 규칙(예: 첫 쪽 전체)으로 블러하므로 관리자가 영역을 고를 수 없다. 영역 지정 UI를 더하면 구현이 커진다. 검증 이슈 #107은 진행하지 않는다.
  - 대안 D: SCR-027의 블러 미리보기 결정과 맞지 않는다.

## 6. 결과

### 기대 효과
- 관리자가 계획안마다 노출 범위를 정할 수 있다(예: 제목·목차는 보이고 주차별 상세만 가림).
- 비인증 방문자는 어떤 경로로도 원본을 받지 못한다(원본을 비공개로 두는 조건 아래).
- 새 의존성·서버 이미지 처리 없이 기존 presigned PUT 업로드 흐름을 재사용한다.

### 감수하는 트레이드오프 / 위험
- 관리자가 매번 블러 이미지를 직접 만들어야 한다(편집 도구·시간 필요).
- 블러가 약한 이미지를 올리면 내용이 노출된다. 서버는 블러 정도를 검사하지 않는다.
- 미리보기와 원본이 다른 달 것으로 짝지어질 수 있다. 등록 화면에서 두 파일을 한 계획안에 함께 올리게 해 위험을 줄인다.

### 후속 작업
- 원본 비공개 저장 위치와 인증 후 전달 방식 정하기. 원본은 공개 사진 CloudFront 경로(`getUrl`)로 내보내지 않는다. → #107에서 서버가 S3에서 읽어 같은 출처 API로 전달하는 방식으로 구현(공개본·원본 모두, 원본은 관리자만).
- 관리자 등록 화면: 월간 계획안은 미리보기와 원본 PDF를 함께 받기(둘 다 필수). → #107에서 `/plans` 화면에 구현, 미리보기는 블러 PDF.
- 계획안 삭제·교체 시 미리보기·원본 파일 정리(ADR-002 방식과 맞추기).
- 대표에게 블러 이미지 만드는 방법 안내(쓸 도구).

## 7. 검증 계획

- 비인증 상태로 FR-032 API를 호출해 응답에 원본 키·URL이 없는지 확인한다(백엔드 테스트).
- 원본 키를 알고 공개 CloudFront 주소로 직접 요청하면 403이 나는지 확인한다(배포 후 점검).
- 대표가 실제 월간 계획안으로 블러 이미지를 만들어 올려 보고, 걸린 시간과 어려운 점을 확인한다.

## 8. 재검토 조건

- 월간 계획안이 비밀이 아니라는 결정이 나 FR-032가 바뀔 때(대안 B 재검토).
- 블러 이미지 제작이 관리자에게 실제로 부담이 되거나, 미리보기·원본 불일치나 블러 부족 이미지 업로드가 생길 때(대안 C에 영역 지정 기능을 더하는 방식 검토).
- 원본 형식이 PDF가 아니게 되거나(이미지, 웹 편집) 등록 건수가 크게 늘 때.

## 9. 이력

- 2026-11-19 — Proposed — 초안 작성. 대안 A(서로 다른 파일), B(원본 하나 + 화면 블러), C(원본 하나 + 서버 생성 미리보기), D(미리보기 없음) 비교.
- 2026-11-19 — Proposed — 결정 책임자 지정. 대안 C 검증을 이슈 #107로 진행.
- 2026-11-19 — Accepted — 대안 A 채택. 블러 영역을 관리자가 직접 골라야 하므로. 대안 C 검증(#107)은 진행하지 않음.
- 2026-11-19 — Accepted — 구현 세부(사용자 결정): 미리보기도 PDF(블러 PDF)로 올리고, 관리자가 /plans 화면에서 등록·수정·삭제. 원본은 기관 인증 전까지 관리자만, PDF는 서버가 같은 출처로 전달하고 pdf.js로 표시. 대안 A 결정은 그대로이며 구현은 #107.
