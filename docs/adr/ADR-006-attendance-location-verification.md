# ADR-006: 직원 출퇴근을 위치로 확인하는 방식

- **상태:** Accepted
- **날짜:** 2026-10-29
- **결정 책임자:** Hi-Imjaeyoung
- **관련 항목:** EMP-FR-001, EMP-FR-010, EMP-FR-011, EMP-FR-012, EMP-FR-002, EMP-FR-003, EMP-FR-004, EMP-FR-007, EMP-SCR-001, EMP-SCR-006, EMP-NFR-001
- **대체 관계:** 없음

## 1. 배경 및 문제

몽키즈 직원은 사무실이 아니라 어린이집·유치원 등 기관으로 직접 가서 수업한다. 관리자는 직원이 할당된 기관에 실제로 도착했는지, 언제 왔다가 떠났는지를 지금 서비스로 확인할 수단이 없다. 근태 관리 요구사항은 "직원의 위치와 할당된 기관 위치를 대조해 출근·퇴근 기록을 저장"하는 것(EMP-FR-001)이다.

원하는 결과는 **관리자가 "이 직원이 이 시각에 이 기관에 있었다"를 믿을 만한 수준으로 확인할 수 있고, 직원은 휴대폰으로 몇 번의 터치만에 출퇴근을 남길 수 있는 것**이다. 이 ADR은 "위치를 어떤 수단으로 받고, 누가 어떻게 판정하며, 판정에 실패하면 어떻게 처리하는가"를 정한다.

## 2. 요구사항 및 제약 조건

### 확인된 사실
- 출근은 하루 한 번이 아니라 **할당된 수업마다** 기록한다(사용자 결정, 2026-10-29). 위치는 그 수업이 열리는 기관 좌표와 대조한다.
- 근태 관리 요구사항은 모두 `기획` 상태다. 착수·확정되지 않았다(`requirement_employee.md`).
- 미결 사항에 "앱인지 웹(모바일 웹)인지", "기관 반경 몇 m를 출근으로 볼지, 위치 권한 거부 시 처리", "홈페이지 직원 권한·로그인을 공유할지"가 남아 있다.
- 직원은 거의 모바일로만 사용한다(EMP-NFR-001).
- 출퇴근 기록에 특이사항을 함께 저장한다(EMP-FR-002). 기록은 작성자 본인과 관리자만 본다(EMP-FR-007).
- 저장소에 기관(위치·주소), 수업 할당(EMP-FR-004), 출퇴근 도메인이 없다. 기관 정보는 상담 신청의 `institution_name`(문자열)뿐이고 좌표가 없다(`back/docs/schema.md`).
- 기존 스택은 Vite + React 웹과 Spring Boot REST API다. 인증은 소셜 로그인 + JWT HttpOnly 쿠키이고, 회원 역할에 `STAFF`가 있다(`back/CLAUDE.md`, FR-022).
- 운영 사이트는 HTTPS로 서비스된다(`docs/deploy-checklist.md`). 브라우저 위치 API(Geolocation)는 HTTPS 같은 보안 컨텍스트에서만 동작한다.
- 브라우저 위치 API는 위도·경도와 함께 정확도 반경(`accuracy`, 미터)을 준다. 이 값이 위조된 것(모의 위치)인지 웹에서 알아낼 방법은 없다. 안드로이드 네이티브 앱은 모의 위치 여부를 확인하는 API가 있다.

### 가정 및 가설
- 가정: 직원 한 명이 하루에 여러 수업(여러 기관)을 맡을 수 있어, 출근 기록이 하루에 여러 건 생긴다. 하루 수업 수는 모른다.
- 퇴근도 수업마다 기록하는지, 하루 마지막 수업 뒤 한 번인지는 정하지 않았다.
- 가정: 직원 수가 적고(대표가 직접 관리하는 규모), 고의적인 위치 위조보다 "깜빡하고 안 찍음", "실내라 위치가 안 잡힘"이 더 흔한 문제다. 확인하지 않았다.
- 가정: 지금은 출퇴근을 메시지·전화 등 사이트 밖에서 보고받거나 확인하지 않는다. 확인하지 않았다.
- 가설: 기관 건물 안·지하 주차장에서는 브라우저 위치 정확도가 나빠져, 엄격한 반경 판정만 쓰면 정상 출근이 거절되는 일이 생긴다. 실제 기관에서 측정한 적은 없다.
- 가설: 직원의 위치 정보를 수집하려면 직원의 동의가 필요하고, 수집·보관 방식에 따라 위치정보 관련 법령상 의무가 생길 수 있다. 법적 요건은 확인하지 않았다.

### 제약 조건 / 비목표
- 출퇴근 순간의 위치만 받는다. 근무 중 실시간·백그라운드 위치 추적은 범위가 아니다.
- 급여·근무시간 정산은 범위가 아니다.
- 기관 데이터 모델과 수업 할당(EMP-FR-004)의 상세 설계는 별도로 정한다. 이 ADR은 "출퇴근 기록이 어떤 할당(또는 기관)을 기준으로 위치를 대조한다"는 것만 전제한다.
- 출근 알림(수신자·수단)은 미결 사항이며 이 ADR 범위가 아니다.

## 3. 결정 요인

- **기록의 신뢰도 (핵심):** 관리자가 기록을 근거로 판단할 수 있어야 한다. 단, 완벽한 위조 방지가 절대 조건인지는 미정이다(열린 질문).
- **직원 사용 마찰 (핵심):** 모바일에서 바로 쓸 수 있고, 위치가 잘 안 잡혀도 출퇴근을 남길 길이 있어야 한다. 정상 출근이 막히면 직원·관리자 모두 사이트 밖으로 돌아간다.
- **개인정보 최소 수집 (절대 제약):** 출퇴근 시점 위치 외에는 받지 않고, 열람은 본인과 관리자로 제한한다(EMP-FR-007). 수집 전에 직원 동의를 받는다.
- **데이터 무결성:** 기록 시각은 서버 시각을 쓴다. 출근 없는 퇴근, 같은 할당에 대한 중복 출근을 서버에서 막는다. 판정은 서버에서 한다.
- **개발·운영 비용 (선호):** 기존 웹 스택과 인증을 재사용할수록 좋다. 앱 스토어 배포·심사, 기기별 대응은 비용이 크다.
- **되돌리는 비용:** 나중에 판정 기준(반경, 정책)이나 수단(웹 → 앱)을 바꿔도 기존 기록이 의미를 잃지 않아야 한다.

## 4. 검토한 대안

### 대안 A — 현상 유지 (위치 확인 기능 없음)
- **접근 방식:** 출퇴근 기능을 만들지 않거나, 만들더라도 직원이 버튼만 눌러 시각을 남기고 위치는 받지 않는다.
- **장점:** 위치 정보 수집에 따른 동의·법적 검토가 필요 없다. 구현이 가장 단순하다.
- **비용 및 위험:** EMP-FR-001의 핵심("위치와 기관 위치를 대조")을 충족하지 못한다. 관리자가 기록을 믿을 근거가 없다.
- **적합한 경우:** 위치 정보 수집에 대한 법적 부담이나 직원 반발이 크다고 확인될 때, 또는 근태 관리 착수 자체가 미뤄질 때.

### 대안 B — 모바일 웹 위치 + 서버 반경 판정, 반경 밖이면 거절 (선택)
- **접근 방식:** 출퇴근 버튼을 누르면 브라우저 위치 API로 좌표·정확도를 받아 서버로 보낸다. 서버가 할당된 기관 좌표와의 거리를 계산해 허용 반경 안이면 저장하고, 밖이거나 정확도가 기준보다 나쁘면 거절한다.
- **장점:** 기존 웹·인증을 그대로 쓴다. 저장된 기록은 모두 "반경 안"이라 관리자가 볼 때 단순하다.
- **비용 및 위험:** 실내·지하에서 위치가 안 잡히면 정상 출근이 막힌다(가설). 위치 권한을 거부하거나 기기 위치가 꺼져 있으면 출퇴근을 남길 수 없다. 기관 좌표가 틀리면 그 기관 직원 모두가 막힌다. 모의 위치 앱으로 좌표를 꾸미는 것은 막지 못한다.
- **적합한 경우:** 실제 기관에서 측정해 보니 위치 정확도가 충분히 좋고, 거절 시 우회 절차(관리자 수동 기록 등)를 따로 둘 때.

#### 대안 B 비용 분석 (출근 단위: 할당된 수업마다)

개발 기간·실패율 같은 수치는 측정하지 않았으므로 적지 않는다. 비용 항목과 그 크기를 좌우하는 조건만 정리한다.

**1. 선행 비용 — 수업 단위 출근이라 먼저 필요한 것** (B만의 비용이 아니라 위치로 확인하는 B·C·D 공통)
- **기관과 좌표:** 기관 엔티티가 없다. 상담 신청의 `institution_name`(문자열)뿐이다(`back/docs/schema.md`). 좌표를 얻는 방법도 정해야 한다. 주소를 지도 API로 변환(외부 API 의존성 추가), 관리자가 지도에서 지정, 좌표 직접 입력 중 하나다.
- **수업 할당(EMP-FR-004)과 수업 회차:** 서버가 "오늘 이 직원의 이 수업, 이 기관"을 가리킬 수 있어야 출근을 대조할 수 있다. 휴강·보강(EMP-FR-005)이 회차를 바꾸므로 반복 일정만으로는 부족하고 날짜별 회차 데이터가 필요하다. 따라서 착수 순서는 기관 → 할당 → 회차 → 출근이다.
- **직원 계정:** 홈페이지 회원의 `STAFF` 역할을 재사용할지 미결이다. 재사용하면 `ArticleWriteSupport`처럼 DB의 현재 역할로 확인하는 기존 방식을 그대로 쓸 수 있다.

**2. B 자체 구현 비용**
- 백엔드: 출퇴근 엔티티(회차, 직원, 출근·퇴근 서버 시각, 좌표·정확도·거리), 거리 계산(하버사인 공식, 새 의존성 없이 Java로 구현), 거절 사유 `ErrorCode`(반경 밖, 정확도 부족, 내 할당 아님, 중복 출근, 출근 없는 퇴근), `SecurityConfig` 경로 추가, 판정 경계값 단위 테스트. 기존 `BusinessException`·`ApiResponse`·`@AuthenticationPrincipal` 방식을 그대로 쓴다.
- 프론트: 브라우저 위치 요청(현재 코드에 사용처 없음), 권한 거부·위치 꺼짐·시간 초과 안내, 거절 사유별 안내와 재시도. 새 의존성은 필요 없다.
- 운영 DB: 운영은 `ddl-auto: validate`이고 Flyway가 없어, 새 테이블마다 배포 전에 RDS에 직접 DDL을 적용해야 한다(`back/docs/database.md`). 선행 도메인까지 합치면 테이블이 여러 개 늘어나므로, database.md가 적어 둔 "이 수작업이 잦아지면 Flyway 도입" 조건에 해당하는지 검토해야 한다.

**3. 숨은 필수 비용 — 거절된 수업의 우회 절차**
- B는 반경 밖이면 아무것도 저장하지 않는다. 우회 절차가 없으면 위치가 안 잡힌 수업은 출근 기록이 통째로 빠진다.
- 그래서 B를 실제로 쓰려면 **관리자 수동 출근 등록**(API + EMP-SCR-006 화면, 누가 왜 등록했는지 기록)이 사실상 필수다. 이를 더하면 B와 C의 구현량 차이는 작다. 차이는 예외를 누가 처리하느냐다. B는 직원이 관리자에게 연락하고 관리자가 직접 입력하며, C는 직원이 사유를 남기고 관리자는 확인만 한다.
- 수업마다 출근하므로 거절이 생길 수 있는 횟수가 하루 수업 수만큼 늘어난다(가설, 실제 거절 비율은 측정 전).

**4. 운영 비용**
- 기관 좌표가 틀리면 그 기관의 모든 수업 출근이 거절된다. 기관을 등록·수정할 때 좌표를 검수해야 한다.
- 거절된 시도를 저장하지 않으므로 적절한 반경을 운영 데이터로 정할 수 없다. 시도 로그를 따로 남기면 사실상 C에 가까워진다.
- 반경·정확도 기준을 코드 상수로 두면 바꿀 때마다 배포해야 한다. 설정값으로 두면 이 비용은 줄어든다.

**5. 되돌리는 비용 (B → C)**
- B에서도 거리·정확도·좌표 원본을 저장해 두면, C로 바꿀 때 판정 결과 컬럼, 사유 필수 입력, 관리자 필터만 추가하면 된다(DDL 1회). 원본을 저장하지 않으면 기존 기록을 다시 판정할 수 없다.
- 원본을 저장할지는 개인정보 최소 수집(결정 요인)과 함께 정한다.

**6. 공통 비용 (B 고유 아님)**
- 위치 정보 수집 동의 문구, 보관 기간, 법적 요건 확인.

**수업 단위 출근으로 새로 생긴 판정 요소**
- 수업 시각 기준으로 출근을 받을 시간 범위를 둘지(수업 시작 전후 언제까지). 범위 값은 정하지 않았다.
- 퇴근 단위(수업마다 / 하루 한 번).

### 대안 C — 모바일 웹 위치 + 서버 판정, 항상 기록하고 판정 결과를 함께 저장
- **접근 방식:** 위치 수집은 대안 B와 같다. 서버는 거절하지 않고 기록을 저장하면서 판정 결과(반경 안 / 반경 밖 / 위치 정확도 부족 / 위치 없음)와 거리·정확도·좌표를 함께 남긴다. 반경 안이 아니면 직원에게 사유(EMP-FR-002 특이사항)를 필수로 받는다. 관리자 화면(EMP-SCR-006)은 판정 결과로 걸러 반경 밖 기록만 확인한다.
- **장점:** 위치가 안 잡혀도 출퇴근 기록과 사유가 남아, 사이트 밖으로 돌아갈 이유가 줄어든다. 판정 기준(반경)을 나중에 바꿔도 거리·정확도 원본이 남아 있어 다시 판정할 수 있다. 실제 운영 데이터로 적절한 반경을 정할 수 있다.
- **비용 및 위험:** 관리자가 반경 밖 기록을 직접 확인해야 한다(운영 부담, 규모는 모름). 대안 B보다 저장하는 위치 정보가 많다(반경 밖 좌표 포함). 모의 위치는 대안 B와 마찬가지로 막지 못한다.
- **적합한 경우:** 직원 규모가 작고 관리자가 예외를 직접 볼 수 있으며, 고의 위조보다 정확도·누락 문제가 더 흔할 때.

### 대안 D — 네이티브(또는 하이브리드) 앱 + OS 위치 API
- **접근 방식:** 출퇴근 전용 앱을 만들어 OS 위치 API로 좌표를 받는다. 안드로이드에서는 모의 위치 여부도 함께 보낸다. 서버 판정은 대안 B 또는 C 방식 중 하나를 쓴다.
- **장점:** 웹보다 위치 권한·정확도를 세밀하게 다룰 수 있고, 안드로이드에서는 모의 위치를 일부 걸러낼 수 있다. 나중에 푸시 알림(출근 알림 미결 사항)과 엮기 쉽다.
- **비용 및 위험:** 앱 개발 스택, 스토어 배포·심사, 기기·OS 버전 대응이 새로 생긴다. 직원이 앱을 설치·업데이트해야 한다. 서버 쪽 판정·기록 설계는 웹과 같으므로, 웹으로 시작해도 이 부분은 그대로 옮겨 갈 수 있다. iOS에서 모의 위치를 확실히 막을 수 있는지는 확인하지 않았다.
- **적합한 경우:** 위치 위조가 실제로 발생해 문제가 되었거나, 푸시 알림 등 앱이 필요한 다른 요구가 확정될 때.

### 대안 E — 기관 현장 QR 코드 확인 (위치 대신 또는 위치와 병행)
- **접근 방식:** 기관마다 고유 QR 코드를 발급해 현장에 두고, 직원이 출퇴근 때 스캔한다. 서버는 코드가 할당된 기관의 것인지 확인한다. 위치는 받지 않거나 보조로만 받는다.
- **장점:** 실내 위치 정확도 문제가 없다. 위치 정보를 수집하지 않아도 된다.
- **비용 및 위험:** 고객 기관에 QR을 붙여 둘 수 있는지 모른다(가정, 확인 안 됨). 코드 사진을 찍어 두면 현장 밖에서도 스캔할 수 있어, 코드 교체·만료 같은 운영이 필요하다. 요구사항의 "위치 기반"과 다르므로 요구사항 변경이 필요하다.
- **적합한 경우:** 기관이 QR 부착에 협조하고, 위치 수집에 대한 부담이 크다고 확인될 때.

### 대안 비교 요약

| 결정 요인 | A 현상 유지 | B 웹·거절 | C 웹·기록+판정 | D 앱 | E QR |
|---|---|---|---|---|---|
| 기록 신뢰도 | 없음 | 반경 안 기록만 남음, 위조 못 막음 | 예외까지 근거와 함께 남음, 위조 못 막음 | 안드로이드 위조 일부 탐지 | 코드 유출 시 무력화 |
| 직원 마찰 | 없음 | 위치 실패 시 막힘 | 위치 실패해도 사유로 기록 | 앱 설치 필요 | 현장 스캔 필요 |
| 위치 수집 범위 | 없음 | 반경 안 좌표 | 모든 시도 좌표 | B 또는 C와 같음 | 없음 또는 보조 |

| 요구사항 변경 | EMP-FR-001 보류 | 없음 | 없음 | 미결 사항(앱/웹) 결정 | "위치 기반" 변경 |

## 5. 결정

- **선택한 대안:** 대안 B — 모바일 웹 위치 + 서버 반경 판정, 반경 밖이면 자동으로 확정하지 않음. 출근은 할당된 수업마다 받는다. 위치로 확인하지 못한 출근은 직원 수동 등록 + 관리자 승인으로 처리한다(대안 C의 사유 등록을 승인 절차와 함께 처음부터 포함).
- **범위:** 이 결정은 **출근**(EMP-FR-001)을 다룬다. 퇴근은 별도 요구사항(EMP-FR-010)으로 분리했고, 지금 범위에서는 고려하지 않는다(EMP-FR-010 보류).
- **조건:**
  - 허용 반경은 **기관 좌표에서 100m**로 넓게 잡는다. 실내·지하에서 위치가 덜 정확해 정상 출근이 거절되는 일(장애)을 줄이기 위해서다. 100m는 측정으로 정한 값이 아니라 여유를 둔 출발값이다.
  - 판정은 **거리만** 본다. 브라우저가 알려 주는 위치 정확도(`accuracy`)가 나빠도 그것만으로 거절하지 않는다.
  - 출근 기록에 **좌표 원본, 기관까지의 거리, 정확도 값을 저장**한다. 관리자가 수동 등록을 승인할지 판단하는 근거이자, 반경 100m를 다시 정할 때(재측정) 쓰는 기준 자료다.
  - **출근 시간은 제한하지 않는다.** 수업 시각과 상관없이 출근을 받고, 서버 시각으로 출근 시각을 기록한다.
  - **위치를 못 받을 때의 안내(EMP-SCR-001):**
    - 위치 권한 거부·위치 꺼짐: 기기·브라우저에서 위치 정보를 켜는 방법을 안내하고 다시 시도하게 한다.
    - 신호가 약함(위치를 못 받음, 시간 초과, 반경 밖으로 거절): 다시 시도하거나 **수동 등록 + 사유 작성**으로 넘어가게 안내한다.
  - **수동 등록은 관리자 승인 후 확정한다(EMP-FR-011).** 직원이 사유와 함께 등록하면 `승인 대기`로 저장한다. 위치를 받았다면 좌표·거리·정확도도 함께 저장한다. 관리자는 이 값과 사유를 보고 승인하거나, 반려하고 다시 출근 시도(재측정)를 요청한다. 관리자가 직접 등록하는 경로도 둔다.
  - **다시 출근 확인(덮어쓰기):** 같은 수업의 출근 기록은 하나만 둔다. 상태에 따라 다시 확인할 수 있는지가 다르다.
    - 저장된 출근 없음(반경 밖으로 거절됨): 덮어쓰기가 아니므로 언제든 다시 시도할 수 있다.
    - 확정(반경 안 자동 확정, 관리자 승인): 다시 확인할 수 없다. 덮어쓰기 불가.
    - 승인 대기: 다시 확인할 수 없다. 관리자 처리를 기다린다.
    - 반려: 다시 확인할 수 있고, 기존 기록(좌표·거리·정확도·시각·상태·사유)을 덮어쓴다. 관리자가 반려하며 다시 출근 시도(재측정)를 요청하는 흐름과 이어진다.
  - **재조정 로그:** 출근 확인 시도마다 좌표·거리·정확도·시각·결과(반경 안 / 반경 밖 / 수동 등록 / 덮어쓰기)를 별도 로그로 남긴다. 덮어쓰기로 출근 기록의 이전 값이 바뀌어도 시도 기록은 로그에 남는다. 로그는 반경 100m 재측정 자료로만 쓰고, 출근 판정·조회에는 쓰지 않는다.
- **근거:** 반경 안 출근은 자동 확정이라 관리자가 볼 기록이 단순하고, 기존 웹·인증을 그대로 쓴다. B의 주된 위험인 "정상 출근이 막혀 기록이 빠지는 것"은 넓은 반경, 위치 켜기 안내, 승인 절차가 있는 수동 등록으로 막는다. 승인 절차가 있으므로 반경 밖 출근이 검토 없이 확정되지 않는다.
- **다른 대안을 선택하지 않은 이유:** A는 EMP-FR-001의 위치 대조를 충족하지 못한다. C(반경 밖도 사유와 함께 바로 기록)는 반경 밖 출근이 검토 없이 확정되므로, 승인 절차를 둔 이번 방식을 택했다. D는 앱 개발·배포 비용이 크고 위치 위조가 실제 문제로 확인되지 않았다. E는 기관 협조가 불확실하고 "위치 기반" 요구사항을 바꿔야 한다.

## 6. 결과

### 기대 효과
- 직원이 휴대폰 브라우저로 수업마다 출근을 남긴다. 반경 100m 안 출근은 자동 확정되고, 위치로 확인하지 못한 출근도 사유와 함께 남아 관리자 승인을 거쳐 확정된다. 출근 기록이 빠지지 않는다.
- 새 앱이나 새 라이브러리 없이 기존 웹 스택과 인증 방식으로 구현한다.

### 감수하는 트레이드오프 / 위험
- **넓은 반경의 대가:** 100m 안이면 기관 건물 밖(근처 주차장·상가 등)에서도 출근이 된다. "기관에 도착했다"의 정밀도를 낮추고 대신 거절을 줄이는 선택이다.
- **승인 부담:** 수동 등록은 관리자가 하나씩 승인해야 한다. 신호 문제가 잦은 기관이 있으면 승인 대기가 쌓인다. 승인 전까지 그 출근은 확정되지 않는다.
- **처음 구현량 증가:** 원래 나중에 넣으려던 사유 등록에 승인 상태(승인 대기 / 승인 / 반려)와 관리자 승인 화면까지 처음부터 만든다.
- **위치 정보 저장량 증가:** 재조정 로그에 반경 밖 시도까지 모든 시도의 좌표가 남는다. 위치 정보 동의 문구와 보관 기간에 로그를 포함해야 하고, 보관 기간이 지나면 지워야 한다.
- **덮어쓰기의 대가:** 반려 후 다시 확인하면 출근 기록의 시각은 마지막으로 확인한 시각이 된다. 이전 값은 로그에만 남는다.
- **승인 대기 중 대기:** 승인 대기 중에는 직원이 다시 시도할 수 없어, 신호가 돌아와도 관리자가 처리할 때까지 출근이 확정되지 않는다.
- 모의 위치 앱으로 좌표를 꾸미는 것은 막지 못한다.

### 후속 작업
- 반경 100m는 코드 상수가 아니라 설정값으로 둔다. 바꿀 때 재배포 범위를 줄이기 위해서다.
- 출근 기록에 좌표 원본·거리·정확도를 저장한다. 수집하는 위치 정보가 늘어나므로 위치 정보 동의 문구와 보관 기간에 이를 포함한다. (결정, 2026-10-29)
- 판정은 거리만 본다(정확도로 거절하지 않음). (결정, 2026-10-29)
- 수동 등록·승인(EMP-FR-011)을 출근 기능과 함께 만든다. 기록에 등록 방식(위치 확인 / 직원 수동 / 관리자 직접), 승인 상태, 사유, 승인·반려한 관리자를 남긴다. 화면은 EMP-SCR-001(직원 등록), EMP-SCR-006(관리자 승인·직접 등록).
- 위치를 못 받을 때의 안내를 만든다: 위치 정보 켜기 안내(기기·브라우저별), 신호가 약할 때 수동 등록 + 사유 작성으로 넘어가는 경로. (결정, 2026-10-29)
- 수업당 출근 기록 1건, 반려된 경우만 다시 확인으로 덮어쓴다. 확정·승인 대기는 덮어쓰기 불가. (결정, 2026-10-29)
- 출근 확인 시도마다 재조정 로그를 남긴다. 로그 보관 기간을 위치 정보 보관 기간 정책에 포함한다. (결정, 2026-10-29)
- 기관 좌표는 관리자가 지도 API로 위치를 찾아 직접 등록·저장한다(EMP-FR-012). 기관 데이터 모델은 EMP-FR-004·EMP-FR-008과 함께 설계한다. (결정, 2026-10-29)
- 지도 API 제공자(카카오·네이버 등)를 고르고 키 관리 방식을 정한다. 외부 API 의존성이 새로 생기므로 구현 전에 확인받는다. 키는 커밋하지 않는다.
- 좌표가 틀리면 그 기관의 모든 출근이 거절되므로, 등록 화면에서 저장 전에 지도에 표시된 위치를 관리자가 확인하게 한다.
- 출근 단위를 할당된 수업마다로 확정하고 `requirement_employee.md`에 반영했다. (완료, 2026-10-29)
- 착수 순서: 기관(좌표) → 수업 할당(EMP-FR-004) → 수업 회차(EMP-FR-005 반영) → 출근(EMP-FR-001, EMP-FR-011)·퇴근(EMP-FR-010).
- 새 테이블이 여러 개 늘어나므로 운영 DB 스키마 변경 방식(수동 DDL 유지 / Flyway 도입)을 검토한다.
- 출근 시간은 제한하지 않고 시각만 기록한다. (결정, 2026-10-29)
- 퇴근은 별도 요구사항 EMP-FR-010으로 분리했고 지금은 고려하지 않는다(보류). (2026-10-29)
- 직원 계정을 홈페이지 회원(`STAFF`)과 공유할지 정한다(미결 사항).
- 위치 정보 수집 동의 문구와 보관 기간을 정하고, 위치정보 관련 법적 요건(동의, 신고 대상 여부)을 확인한다.
- EMP-FR-001 설명과 미결 사항(위치 판정 기준)을 갱신하고 이 ADR을 연결했다. (완료, 2026-10-29)

## 7. 검증 계획

- 도입 전, 가능하면 실제 할당 기관 2~3곳에서 출입구·교실·주차장 위치별로 브라우저 위치 API의 좌표와 `accuracy` 값을 기록해, 반경 100m 안에 드는지 확인한다.
- 도입 후, 재조정 로그를 기관별로 모아 거리·정확도 분포를 본다. 반경 100m를 늘리거나 줄일지(재측정) 판단하는 근거다.
- 직원이 쓰는 기기(안드로이드·iOS, 주요 브라우저)에서 위치 권한 요청·거부·재허용 흐름을 직접 확인한다.
- 도입 후 승인 대기 건수와 승인까지 걸린 시간을 본다. 관리자 승인 부담이 감당할 만한지 판단한다.
- 위치 권한 거부·위치 꺼짐·시간 초과 상황을 기기별로 재현해, 안내 문구대로 위치를 켜고 다시 시도할 수 있는지 확인한다.
- 대표에게 확인한다: 직원 한 명의 하루 수업 수.
- 서버 판정 로직(거리 계산, 100m 경계값, 같은 수업 다시 확인 시 반려 상태만 덮어쓰고 확정·승인 대기는 거절, 시도마다 로그 기록, 수동 등록 상태 전이 승인 대기 → 승인 / 반려)을 단위 테스트로 검증한다.

## 8. 재검토 조건

- 특정 기관에서 수동 등록이 반복되어, 저장된 거리·정확도로 볼 때 반경이 맞지 않을 때 (반경 재측정 또는 기관별 반경 검토).
- 승인 대기가 쌓여 관리자가 감당하기 어려울 때 (승인 없이 사유만 남기는 대안 C 방식 검토).
- 반경 100m 때문에 기관에 도착하지 않고도 출근하는 일이 확인될 때 (반경 축소 검토).
- 측정 결과 대부분의 기관에서 위치 정확도가 반경 판정에 쓸 수 없을 만큼 나쁠 때 (대안 E 또는 다른 확인 수단 검토).
- 위치 위조가 실제로 확인되었을 때 (대안 D 검토).
- 앱/웹 미결 사항이 다른 이유(푸시 알림 등)로 앱으로 결정되었을 때.
- 위치정보 관련 법적 검토에서 수집 방식에 제약이 확인되었을 때.
- 직원 수가 늘어 관리자가 반경 밖 기록을 직접 확인하기 어려워질 때.

## 9. 이력

- 2026-10-29 — Proposed — 초안 작성.
- 2026-10-29 — Proposed — 출근 단위(할당된 수업마다) 반영, 대안 B 비용 분석 추가.
- 2026-10-29 — Accepted — 대안 B 승인. 허용 반경 100m, 신호 문제 발생 시 대안 C의 사유 등록 기능을 나중에 추가.
- 2026-10-29 — Accepted — 미정으로 남겼던 거절된 출근 처리 방법 확정: 관리자 수동 출근 등록을 처음부터 포함 (선택한 대안은 그대로).
- 2026-10-29 — Accepted — 세부 조건 확정: 좌표 원본 저장, 판정은 거리만(정확도로 거절 안 함), 출근 시간 제한 없이 시각만 기록. 결정 책임자 기록 (선택한 대안은 그대로).
- 2026-10-29 — Accepted — 보완: 퇴근을 EMP-FR-010으로 분리(이 ADR은 출근만). 거리·정확도 값 저장(승인 판단·반경 재측정 기준). 위치를 못 받을 때 위치 켜기 안내, 신호가 약하면 직원 수동 등록 + 사유 작성 → 관리자 승인(EMP-FR-011). "사유 등록 기능은 나중에 추가" 조건을 "승인 절차와 함께 처음부터 포함"으로 바꿈. 반경 밖 자동 확정 안 함(대안 B)은 유지.
- 2026-10-29 — Accepted — 보완: 정확도·위치가 부정확했으면 직원이 같은 수업에 다시 출근 확인 가능, 기존 기록을 덮어씀(수업당 출근 기록 1건).
- 2026-10-29 — Accepted — 보완: 확정·승인 대기 출근은 덮어쓰기 불가, 반려된 경우만 다시 확인 가능. 시도마다 재조정 로그 기록. 퇴근(EMP-FR-010) 보류.
- 2026-10-29 — Accepted — 보완: 기관 좌표는 관리자가 지도 API로 직접 등록·저장(EMP-FR-012). 지도 API 제공자는 미정.
