# ADR-008: 관리자의 정적 리소스(문구·사진) 웹 편집 방식

- **상태:** Accepted
- **날짜:** 2026-11-18
- **결정 책임자:** Hi-ImJeaYoung
- **관련 항목:** 회의록 2026-11-12 "그 외 1" → [requirement_homepage.md](../requirements/requirement_homepage.md) 미결 사항 "정적 리소스(문구·사진) 웹 편집", [ADR-002](ADR-002-s3-orphan-photo-cleanup.md)(S3 사진 정리)
- **대체 관계:** 없음

## 1. 배경 및 문제

홈페이지 화면의 문구·사진(히어로 문구와 사진, 프로그램 소개, 강사 카드, FAQ 등)은 코드 안의 정적 데이터다. 지금은 문구 하나, 사진 한 장을 바꾸려 해도 개발자가 코드를 고치고 PR을 병합해 배포해야 한다. 대표(관리자)는 웹에서 직접 고칠 수 있는지 물었다.

원하는 결과는 다음과 같다.
- 홈 히어로 글귀를 대표가 개발자를 거치지 않고 빨리 바꾼다.
- 개발자가 아닌 사람도 헷갈리지 않고 고칠 수 있다.
- 잘못 고쳐도 사이트가 깨지지 않는다.
- 월 운영 예산과 1인 개발 규모를 넘지 않는다.

편집 대상은 **홈(SCR-001) 히어로 글귀만**이다. 사진 변경은 요구사항에서 제외했다(결정 책임자 확인, 2026-11-18). 글귀가 얼마나 자주 바뀌는지는 아직 모른다.

> **범위 확장 (2026-11-19, 결정 책임자):** 같은 방식(대안 C: 코드 기본값 + DB 덮어쓰기)을 ABOUT 몽키즈(SCR-002) 월별 커리큘럼 예시 3줄(월·활동 주제)에도 적용한다(FR-034, #101). 편집 화면은 관리자 화면 메뉴가 아니라 ABOUT 화면 패널 안에서 바로 고치는 방식이고, 줄 수는 3줄 고정이다. 결정(대안 C) 자체는 바뀌지 않는다.

## 2. 요구사항 및 제약 조건

### 확인된 사실
- 화면 문구·수치·목록은 `front/src/data/*.js`(14개 파일: `homeContent.js`, `aboutContent.js`, `programContent.js`, `faqContent.js`, `privacyContent.js` 등)에 정적 데이터로 둔다. 컴포넌트에 하드코딩하지 않는 것이 프론트 규칙이다(`front/CLAUDE.md`).
- 화면 사진은 `front/src/assets/`에 두고 Vite가 빌드할 때 묶는다. 바꾸려면 다시 빌드·배포해야 한다.
- `main`에 병합하면 GitHub Actions가 프론트를 S3 + CloudFront에 자동 배포한다(`docs/git-workflow.md` 4절).
- 게시물·후기 사진은 이미 S3 Presigned URL로 올리고 서버가 저장한다(`back/.../global/storage/S3FileStorage.java`, FR-008·FR-015). 업로드 경로를 재사용할 수 있다.
- 관리자 화면(SCR-014, `/admin`)과 관리자 권한 검사(DB 역할 기준)가 이미 있다.
- 월 운영 예산 상한은 50,000~100,000원이다(requirement_homepage.md 제약 사항).
- 홈페이지 MVP 범위는 확정됐다(2026-10-29).
- 편집 대상은 홈 히어로 글귀뿐이고 사진은 제외한다(결정 책임자 확인, 2026-11-18).
- 히어로 글귀는 `homeContent.js`의 `hero` 객체다: 두 줄 제목 `titleLines`(둘째 줄은 `highlight`로 노란 밑줄 강조), 설명 `description`, 운영 지역 `area`.

### 가정 및 가설
- 가정: "히어로 글귀"는 제목 두 줄과 설명 한 줄을 뜻하고, 운영 지역(`area`)은 포함하지 않는다. 확인이 필요하다.
- 가정: 수정 빈도는 월 몇 번 이하다. 측정하지 않았다.
- 가설: 편집 항목이 몇 칸뿐이면, 화면과 같은 모양의 입력칸(제목 1줄·2줄·설명)만 보여 주는 편집 화면이 비개발자에게 가장 쉽다.
- 가설: 정적 데이터 전체를 DB로 옮겨도 비개발자가 쉽게 고칠 수 있게 되지는 않는다. 14개 파일의 배열·중첩 구조가 그대로 편집 화면의 복잡도로 옮겨 가고, 어느 칸이 화면의 어디인지 알기 어렵기 때문이다(결정 책임자 의견, 2026-11-18. 사용자 검증은 하지 않았다).

### 제약 조건 / 비목표
- 사진 교체는 비목표다(2026-11-18).
- 히어로 외 화면의 문구 편집은 이번 범위가 아니다. 필요해지면 재검토한다.
- 화면 배치·섹션 순서·디자인을 웹에서 바꾸는 페이지 빌더는 비목표다.
- 수업 현장·연구소 게시물, 후기처럼 이미 서버에 저장하는 콘텐츠는 대상이 아니다.
- 개인정보처리방침(SCR-023)처럼 법적 고지 문구는 이력 관리가 필요하므로 이번 대상에서 뺀다.

## 3. 결정 요인

- **수정 속도(핵심):** 대표가 바꾸고 싶을 때 개발자 없이 바로 반영되어야 한다.
- **비개발자 사용성(핵심):** 입력칸이 화면의 어느 글귀인지 바로 알 수 있고, 저장 전에 결과를 볼 수 있어야 한다.
- **안전성(절대 제약):** 잘못된 입력으로 화면이 깨지거나 비어 보이면 안 된다. 입력 검증과 되돌리기가 필요하다.
- **개발 기간과 복잡도:** 1인 개발. 근태 관리 등 진행 중인 일을 막지 않는 규모여야 한다.
- **운영 비용:** 월 예산 상한 안. 외부 유료 서비스는 선호하지 않는다.
- **성능:** 정적 번들로 바로 그리던 화면이 API 응답을 기다리느라 느려지거나 깜빡이지 않아야 한다. 선호 사항이다.
- **변경 용이성:** 나중에 편집 대상을 늘리거나 줄이기 쉬워야 한다.

## 4. 검토한 대안

### 대안 A — 현상 유지 (수정 요청 → 개발자 반영)
- **접근 방식:** 대표가 바꿀 내용을 전달하면 개발자가 `data/`·`assets/`를 고쳐 PR을 병합하고, 자동 배포로 반영한다.
- **장점:** 추가 개발이 없다. 모든 변경이 리뷰·이력(git)에 남고 빌드 검증을 거친다.
- **비용 및 위험:** 반영이 개발자 일정에 묶인다. 작은 변경도 PR 한 번이 필요하다.
- **적합한 경우:** 수정이 드물고 개발자가 빨리 대응할 수 있을 때.

### 대안 B — 정해진 사진 자리만 관리자 교체 (범위 밖)

> 사진 변경이 요구사항에서 빠져(2026-11-18) 더 검토하지 않는다. 기록으로만 남긴다.

- **접근 방식:** 히어로·강사 카드처럼 정해진 사진 자리(슬롯)마다 키를 두고, 관리자 화면에서 사진을 올리면 S3에 저장하고 키에 연결한다. 화면은 등록된 사진이 있으면 그 사진, 없으면 지금의 번들 사진을 쓴다. 문구는 대안 A로 처리한다.
- **장점:** 기존 S3 업로드 경로와 관리자 화면을 재사용해 작업량이 작다. 사진이 없거나 오류가 나도 기본 사진으로 그려져 화면이 깨지지 않는다.
- **비용 및 위험:** 문구는 여전히 개발자가 바꿔야 한다. 사진 슬롯 조회 API 1회가 추가되어 첫 화면에서 기본 사진 → 새 사진으로 바뀌는 깜빡임이 생길 수 있다. 교체된 이전 사진의 S3 정리가 필요하다(ADR-002 방식과 맞춤).
- **적합한 경우:** 바꾸고 싶은 것이 주로 사진일 때.

### 대안 C — 히어로 글귀만 덮어쓰기 (전용 편집 화면) (선택)
- **접근 방식:** `homeContent.js`의 `hero` 글귀를 기본값으로 그대로 두고, 관리자가 저장한 히어로 글귀(제목 1줄·제목 2줄·설명)만 DB에 한 건으로 저장한다. 홈은 저장된 값이 있으면 그것을, 없으면 기본값을 쓴다. 관리자 화면(SCR-014)에 히어로 모양 그대로의 입력칸과 미리보기, "기본 문구로 되돌리기"를 두고, 줄마다 길이 제한을 검증한다.
- **장점:** 편집 칸이 화면과 1:1이라 비개발자도 헷갈리지 않는다. 저장 대상이 한 건이라 서버·화면 작업이 작다. 기본값이 코드에 남아 있어 장애·오입력 때 바로 복원된다.
- **비용 및 위험:** 히어로 조회 API 1회가 추가되어 첫 화면에서 기본 글귀 → 저장 글귀로 바뀌는 깜빡임이 생길 수 있다(응답 전에는 글귀 자리를 비워 두는 등으로 완화). 글귀가 코드와 DB 두 곳에 있어 개발자가 기본값을 고쳐도 저장 글귀가 있으면 화면에 안 나온다. 변경 이력은 git이 아니라 DB에 남으므로 이전 값 보관 여부를 정해야 한다. 히어로 외 문구로 넓히려면 항목마다 편집 화면을 추가해야 한다.
- **적합한 경우:** 바꾸는 글귀가 히어로처럼 몇 칸으로 정해져 있을 때.

### 대안 D — 정적 데이터 전체를 DB·관리자 편집으로 전환 (자체 CMS)
- **접근 방식:** `data/*.js` 대부분을 DB로 옮기고 화면별 편집 화면을 만든다.
- **장점:** 거의 모든 문구·목록을 웹에서 바꿀 수 있다.
- **비용 및 위험:** 14개 데이터 파일의 구조(배열·중첩 객체)를 모두 스키마와 편집 UI로 옮겨야 해서 작업량이 가장 크다. 모든 화면이 API에 의존하게 되어 장애 영향이 커지고 첫 화면이 느려질 수 있다. 화면 구조를 바꿀 때마다 스키마도 고쳐야 한다. DB로 옮긴다고 비개발자가 쉽게 고칠 수 있게 되지는 않는다: 데이터 구조가 편집 화면에 그대로 드러나 항목이 많고, 어느 칸이 화면의 어디인지 알기 어렵다(결정 책임자 의견). 편집 대상이 히어로 글귀뿐이라 요구보다 지나치게 크다.
- **적합한 경우:** 콘텐츠 운영 인력이 따로 있고 수정 범위가 넓을 때.

### 대안 E — 외부 헤드리스 CMS 도입
- **접근 방식:** 외부 CMS(Contentful, Strapi Cloud 등)에서 콘텐츠를 관리하고 프론트가 그 API를 읽는다.
- **장점:** 편집 화면·이력·이미지 관리를 직접 만들지 않는다.
- **비용 및 위험:** 새 의존성과 별도 계정·권한 관리가 생긴다. 무료 한도·요금은 확인하지 않았으며 예산 상한을 넘을 수 있다. 관리자 계정이 홈페이지와 분리된다. 데이터 구조 이전 작업은 D와 비슷하다. 히어로 글귀 몇 칸을 위해 들이기에는 지나치게 크다.
- **적합한 경우:** 콘텐츠 양이 많고 외부 서비스 비용을 감당할 수 있을 때.

## 5. 결정

- **선택한 대안:** 대안 C — 히어로 글귀만 덮어쓰기 (전용 편집 화면)
- **근거:** 바꾸는 대상이 히어로 글귀(텍스트) 몇 칸뿐이라 구현 비용이 크지 않다고 판단했다(결정 책임자, 2026-11-19). 저장 대상이 한 건이고, 기존 관리자 화면(SCR-014)과 권한 검사를 재사용하며, 기본값이 코드에 남아 오입력·장애 때 바로 복원된다. 대표가 개발자 없이 바로 바꿀 수 있어 수정 속도·비개발자 사용성 요인을 충족한다.
- **다른 대안을 선택하지 않은 이유:**
  - A(현상 유지): 반영이 개발자 일정에 묶여 핵심 요인인 수정 속도를 충족하지 못한다. C의 비용이 작아 굳이 감수할 이유가 없다고 봤다.
  - B: 사진 변경이 요구사항에서 빠져 범위 밖이다.
  - D(자체 CMS): 편집 대상이 히어로 글귀뿐인데 작업량·장애 영향이 가장 크고, 비개발자 사용성도 나아지지 않는다.
  - E(외부 CMS): 새 의존성·별도 계정·예산 불확실성을 히어로 글귀 몇 칸을 위해 들이기에는 지나치게 크다.

## 6. 결과

### 기대 효과
- 대표가 관리자 화면에서 홈 히어로 글귀를 직접 바꾸고 곧바로 반영할 수 있다.
- 입력칸이 화면과 1:1이고 미리보기가 있어 설명 없이도 고칠 수 있다.
- 저장 값이 없거나 조회에 실패하면 코드의 기본 글귀로 그려져 화면이 깨지지 않는다.

### 감수하는 트레이드오프 / 위험
- 히어로 조회 API 1회가 추가되어 첫 화면에서 기본 글귀 → 저장 글귀로 바뀌는 깜빡임이 생길 수 있다. 응답 전에는 글귀 자리를 비워 두는 등으로 완화한다.
- 글귀가 코드(기본값)와 DB(저장 값) 두 곳에 있다. 저장 값이 있으면 개발자가 기본값을 고쳐도 화면에 나오지 않는다.
- 변경 이력이 git이 아니라 DB에 남는다. 이전 값 보관 여부는 아직 정하지 않았다.
- 히어로 외 문구로 넓히려면 항목마다 편집 화면을 추가해야 한다.

### 후속 작업
- 히어로 글귀 편집을 requirement_homepage.md에 SCR(SCR-001·014)·FR로 반영하고, 미결 사항 "정적 리소스(문구·사진) 웹 편집"을 해소로 옮긴다.
- 운영 지역(`area`)을 편집 대상에 넣을지 결정 책임자에게 확인한다.
- 이전 값 보관 여부(최근 1건만 / 이력 테이블)를 구현 전에 정한다.
- 줄마다 길이 제한 값을 디자인 기준으로 정한다.

## 7. 검증 계획

- "히어로 글귀"에 운영 지역(`area`)이 들어가는지 결정 책임자에게 확인한다.
- git 이력에서 `homeContent.js`의 `hero` 변경 횟수를 세어 실제 수정 빈도를 확인한다(A로 충분한지 가르는 근거).
- C를 고르면, 대표가 관리자 화면에서 글귀를 직접 바꿔 보게 해 설명 없이 고칠 수 있는지, 첫 화면 깜빡임과 "기본 문구로 되돌리기"가 동작하는지 확인한다.
