# ADR-003: 사진 업로드 경로 — Presigned URL 직접 업로드

- **상태:** Accepted
- **날짜:** 2026-10-24
- **결정 책임자:** 저장소 관리자 (Hi-Imjaeyoung)
- **관련 항목:** FR-008, FR-015, NFR-001 / ADR-001 (사진 키 소유 보장 후속 작업) / ADR-002 (고아 사진 정리) / `back/docs/architecture.md` 8절
- **대체 관계:** 없음

## 1. 배경 및 문제

게시물·연구소 글·후기에는 사진을 붙인다. 장당 최대 10MB, 게시물·연구소 글은 글당 20장, 후기는 5장까지다 (FR-008, FR-015). 사진은 S3에 두고 DB에는 객체 키만 저장한다.

이 사진 파일이 브라우저에서 S3까지 어떤 경로로 가는지를 정해야 한다. 지금은 서버가 서명한 업로드 URL(Presigned URL)을 브라우저에 주고, 브라우저가 S3에 직접 올린다. 이 방식은 이미 구현되어 있으나, 왜 이 방식을 택했고 무엇을 감수하는지 기록한 문서가 없다. ADR-002는 업로드 방식을 바꾸지 않는 전제로만 두었다.

원하는 결과는 다음과 같다.

1. 사진 파일 전송이 백엔드(EC2 한 대)의 대역폭·메모리·요청 처리에 부담을 주지 않는다.
2. 허용한 형식·크기의 사진만 저장소에 들어간다.
3. 업로드했지만 글에 쓰이지 않은 객체(고아 객체)가 생기는 경우를 줄이거나, 적어도 어떤 경우에 생기는지 알고 감수한다.

## 2. 요구사항 및 제약 조건

### 확인된 사실
- 업로드 흐름: 작성 화면이 `POST /api/v1/{posts,lab-posts,reviews}/image-upload-urls`로 `{contentType, size}` 목록을 보내 `[{imageKey, uploadUrl}]`을 받고, 브라우저가 `uploadUrl`에 PUT으로 올린다. 글을 저장할 때 키만 보낸다 (`back/docs/architecture.md` 8절, `back/docs/api-guidelines.md`, `front/src/api/posts.js`).
- Presigned URL에는 `Content-Type`·`Content-Length`를 서명해서, 다른 형식·크기로 올리면 S3가 거부한다. 유효 시간은 10분이다 (`S3FileStorage`, `StorageProperties`).
- 저장할 때 서버는 키 접두사, 중복, 객체 존재(`HeadObject`), 크기를 다시 확인한다 (`ArticleWriteSupport`, `ReviewService`). 키를 이 글을 위해 발급했는지(소유)는 확인하지 않는다 (ADR-001, ADR-002).
- 업로드 시점이 화면마다 다르다.
  - 게시물·연구소 글 편집기는 사진을 본문에 넣는 순간 S3에 올린다. 미리보기는 로컬 파일(`URL.createObjectURL`)로 보여 준다 (`front/src/components/news/PostContentEditor.jsx` `addPhotos`).
  - 후기는 제출 버튼을 눌렀을 때 사진을 올리고 바로 저장 요청을 보낸다 (`front/src/components/review/ReviewFormModal.jsx` `submit`).
- 운영 구성: API는 CloudFront → Caddy → Spring Boot(EC2 t4g.small 한 대), 사진은 별도 CloudFront(OAC)로만 읽고 버킷은 비공개다 (`docs/deploy-checklist.md`).
- 백엔드 IAM 권한은 `posts/*`, `lab/*`, `reviews/*`에 `s3:PutObject`, `s3:GetObject`뿐이다 (`docs/deploy-checklist.md` H).
- 업로드 후 저장하지 않은 객체는 지우지 않는다 (ADR-002, 현상 유지).
- 성능 요구는 동시 접속 30명 내외다 (NFR-001).

### 가정 및 가설
- 가정: 업로드 방식을 고른 주된 이유는 "네트워크 비용 절감"이다 (사용자 설명). 요금 기준인지 서버 대역폭·부하 기준인지는 정하지 않았다.
- 가설: 실제 이득은 AWS 전송 요금보다 EC2의 대역폭·메모리·요청 처리 시간을 쓰지 않는 데서 더 크다. 요금은 계산하거나 측정하지 않았다.
- 가정: 사진 업로드 빈도와 용량은 많지 않다. 운영에서 측정하지 않았다.
- 가설: 게시물 편집기에서 사진을 넣었다가 빼거나 작성을 취소하는 경우가 고아 객체의 주된 원인이다. 측정하지 않았다.

### 제약 조건 / 비목표
- 고아 객체를 지우는 방식은 ADR-002에서 다룬다. 이 ADR은 고아가 생기는 경우와 양에만 관여한다.
- 사진 키 소유 보장 설계는 ADR-001 후속 작업이다.
- 이미지 리사이즈·썸네일·형식 변환은 범위가 아니다.
- 사진 읽기 경로(CloudFront OAC)와 키 형식은 바꾸지 않는다.

## 3. 결정 요인

- **업로드 검증 (절대 제약):** 허용한 형식·크기를 넘는 파일이 저장소에 들어가거나 글에 붙으면 안 된다.
- **보안 (절대 제약):** 버킷은 비공개를 유지하고, 브라우저가 받는 쓰기 권한은 서버가 정한 키 하나·짧은 시간으로 한정한다.
- **서버 부담 (선호, 비중 높음):** EC2 한 대가 API·인증·DB 접근을 모두 맡는다. 큰 요청 본문(글 한 개에 최대 200MB)이 이 서버를 지나면 다른 요청에 영향을 줄 수 있다.
- **고아 객체 발생 범위 (선호):** 정리를 하지 않는 동안(ADR-002) 생기는 고아는 계속 쌓인다.
- **실패 처리와 사용자 경험 (선호):** 업로드 실패를 어디서 알리고 다시 시도할 수 있는지, 저장 버튼 이후 대기 시간이 얼마나 되는지.
- **구현·운영 복잡도 (선호):** 이미 구현된 흐름을 바꾸는 비용, 프록시·CloudFront 설정 변경, 테스트 방식(`@MockitoBean FileStorage`).

## 4. 검토한 대안

### 대안 A — 현상 유지: Presigned PUT 직접 업로드, 게시물은 넣는 즉시 업로드
- **접근 방식:** 지금 흐름 그대로. 서버는 URL 발급과 저장 시 검증만 하고, 파일은 브라우저 → S3로 간다. 게시물 편집기는 사진을 넣을 때, 후기는 제출할 때 올린다.
- **장점:** 사진 파일이 EC2를 지나지 않는다. 형식·크기를 S3가 서명으로 강제하고 저장 시 서버가 다시 확인한다. 게시물 저장 요청이 가볍고, 업로드 실패를 사진을 넣는 순간 알 수 있다. 바꿀 것이 없다.
- **비용 및 위험:** 업로드와 저장이 분리되어, 저장하지 않으면 고아가 생긴다. 게시물은 넣는 즉시 올리므로 작성 취소, 편집 중 사진 제거, 저장 실패가 모두 고아를 만든다. 서버가 키 소유를 확인하지 않는다 (ADR-001). 브라우저가 S3 도메인에 직접 요청하므로 버킷 CORS 설정이 필요하다.
- **되돌리는 비용:** 해당 없음.
- **적합한 경우:** 서버 부담을 피하는 것이 가장 중요하고, 고아 객체를 당분간 감수할 수 있는 경우.

### 대안 B — 서버 경유 업로드
- **접근 방식:** 브라우저가 사진을 multipart로 API에 보내고, 서버가 S3에 `PutObject`한다. 사진만 먼저 올리는 엔드포인트를 두거나, 글 저장 요청에 사진을 함께 실을 수 있다.
- **장점:** 서버가 파일 내용을 직접 보므로 형식 검사(매직 바이트)·가공을 할 수 있다. 글 저장과 함께 실으면, 작성 취소나 편집 중 제거로는 고아가 생기지 않는다. 브라우저가 S3에 직접 접근하지 않아 버킷 CORS가 필요 없다.
- **비용 및 위험:** 모든 사진이 CloudFront → Caddy → Spring → S3를 지나 EC2 대역폭·메모리·요청 처리 시간을 쓴다. 글 하나가 최대 200MB 요청이 될 수 있어 Spring multipart 한도, Caddy·CloudFront의 요청 크기·시간 제한을 손봐야 하고, 업로드 중 다른 요청이 느려질 수 있다 (측정하지 않음). 저장 요청에 실어도 S3 저장과 DB 커밋은 한 트랜잭션이 아니어서, 커밋 실패 시 고아는 여전히 생긴다. 프론트·백의 업로드 흐름을 모두 다시 만들어야 한다.
- **되돌리는 비용:** 높다. 업로드 API와 프론트 흐름을 다시 바꿔야 한다.
- **적합한 경우:** 서버에서 사진을 가공하거나 내용 검사를 해야 하는 요구가 생기고, 서버를 늘릴 수 있는 경우.

### 대안 C — Presigned 직접 업로드 + 게시물도 제출 시점에 업로드
- **접근 방식:** 업로드 경로는 A와 같다. 게시물·연구소 편집기도 후기처럼 사진을 넣을 때는 로컬 파일만 들고 있다가, 저장 버튼을 누르면 업로드 URL을 받아 올리고 키를 본문에 채운 뒤 저장한다.
- **장점:** 사진 파일이 EC2를 지나지 않는다(A와 같음). 작성 취소와 편집 중 사진 제거로는 고아가 생기지 않고, "업로드는 성공했지만 저장이 실패한 경우"만 남는다. 후기와 게시물의 업로드 시점이 같아진다. 미리보기는 이미 로컬 파일로 하고 있다.
- **비용 및 위험:** 편집기의 사진 노드가 저장 전까지 키 없이 로컬 파일을 들고 있어야 하고, 저장 직전에 본문 HTML의 `data-image-key`를 채우는 단계가 생긴다 (`photoGroupExtension.js`, `PostContentEditor.jsx` 수정). 사진이 많으면 저장 버튼 이후 대기가 길어지고, 업로드 실패를 저장할 때에야 알게 된다. 업로드 URL 유효 시간(10분)은 발급 직후 올리므로 문제되지 않는다. 기존 고아와 저장 실패 고아는 여전히 ADR-002의 범위로 남는다.
- **되돌리는 비용:** 중간. 프론트 편집기만 바뀌고 백엔드 API는 그대로다.
- **적합한 경우:** 서버 부담은 A 수준으로 두면서, 정리 기능 없이 고아가 생기는 경우를 줄이고 싶은 경우.

### 함께 검토했지만 대안으로 두지 않은 변형
- **Presigned POST(정책 문서):** `content-length-range`나 태그 조건을 정책으로 표현할 수 있다. 지금 요구(정확한 형식·크기)는 PUT 서명으로 이미 강제되고, 업로드 경로와 고아 발생은 A와 같아서 따로 두지 않았다. ADR-002 대안 B(태그 + 수명 주기)를 고르게 되면 다시 볼 수 있다.

### 결정 요인별 비교

| 결정 요인 | A — 현상 유지 | B — 서버 경유 | C — 직접 업로드 + 제출 시점 |
|---|---|---|---|
| 업로드 검증 | S3 서명 + 저장 시 확인 | 서버가 직접 확인(내용 검사 가능) | A와 같음 |
| 보안 | 키 하나·10분 쓰기 URL, 버킷 CORS 필요 | 브라우저 쓰기 권한 없음 | A와 같음 |
| 서버 부담 | 파일이 서버를 지나지 않음 | 모든 파일이 EC2를 지남 | A와 같음 |
| 작성 취소·편집 중 제거 | 고아 생김 (게시물) | 저장과 함께 실으면 안 생김 | 안 생김 |
| 저장 실패 | 고아 생김 | 고아 생김 | 고아 생김 |
| 업로드 실패 알림 | 사진을 넣을 때 | 저장할 때 | 저장할 때 |
| 변경 범위 | 없음 | 프론트·백 업로드 흐름, 프록시·CloudFront 한도 | 프론트 편집기 |

## 5. 결정

- **선택한 대안:** 대안 A — 현상 유지. Presigned PUT 직접 업로드와 게시물 편집기의 "넣는 즉시 업로드"를 그대로 둔다. 고아 객체 처리 방안은 후속 작업으로 검토한다 (사용자 결정, 2026-10-24).
- **근거:** 절대 제약인 업로드 검증(서명된 형식·크기 + 저장 시 재확인)과 보안(키 하나·10분 쓰기 URL, 비공개 버킷)을 이미 충족한다. 비중이 높은 서버 부담 면에서 사진 파일이 EC2 한 대를 지나지 않는다. 바꿀 것이 없어 비용과 위험이 가장 작다. 남는 약점인 고아 객체는 업로드 경로가 아니라 업로드 시점(C)이나 정리 방식(ADR-002)으로 다룰 수 있어서, 경로 결정과 분리해 나중에 검토해도 이 결정을 되돌릴 필요가 없다.
- **다른 대안을 선택하지 않은 이유:**
  - B(서버 경유): 모든 사진이 EC2를 지나 서버 부담 요인에 가장 불리하고, 프론트·백 업로드 흐름과 프록시·CloudFront 한도를 모두 바꿔야 한다. 저장 실패 고아도 없어지지 않는다. 서버 측 사진 가공·내용 검사 요구가 없다.
  - C(제출 시점 업로드): 경로는 A와 같아 이 결정과 충돌하지 않는다. 고아를 줄이는 방법으로서의 가치는 후속 고아 처리 검토에서 ADR-002의 정리 방식과 함께 비교한다.

## 6. 결과

### 기대 효과
- 사진 전송이 서버 부담과 분리된 상태가 유지된다.
- 코드·설정·권한 변경이 없다.
- 업로드 실패를 사진을 넣는 순간 알 수 있다 (게시물).

### 감수하는 트레이드오프 / 위험
- 게시물·연구소 글에서 작성 취소, 편집 중 사진 제거, 저장 실패가 고아 객체를 만든다. 후기는 저장 실패만 고아를 만든다. 정리는 ADR-002가 정한 대로 당분간 하지 않으므로 고아가 계속 쌓인다. 양은 측정하지 않았다.
- 서버가 키 소유를 확인하지 않는 문제는 업로드 경로와 별개로 남는다 (ADR-001 후속).
- "네트워크 비용 절감"의 실제 크기(요금, 서버 부하)는 측정하지 않았다 (2절 가정·가설).

### 후속 작업
- 고아 객체 처리 방안 검토: 업로드 시점 변경(이 ADR의 대안 C)과 정리 방식(ADR-002 대안 B~D)을 함께 비교해 새 ADR로 결정한다. 정리 방식이 바뀌면 그 ADR이 ADR-002를 대체한다.
- `back/docs/architecture.md` 8절에서 이 ADR을 링크한다. (2026-10-24 완료)

## 7. 검증 계획

- 운영 버킷의 `posts/`·`lab/`·`reviews/` 객체 수와 세 사진 테이블 행 수를 비교해 고아가 얼마나 생기는지 잰다 (ADR-002 7절과 같은 측정).
- "네트워크 비용"을 요금 기준으로 판단하려면, AWS 비용 탐색기에서 EC2·S3·CloudFront 데이터 전송 항목을 확인한다. 지금은 수치가 없다.
- C를 검토한다면 개발 환경에서 편집기 프로토타입으로 사진 20장을 저장할 때 대기 시간과 실패 시 동작(일부만 업로드된 경우)을 확인한다.
- B를 검토한다면 개발 환경에서 큰 multipart 요청 중 다른 API의 응답 시간을 관찰한다.
