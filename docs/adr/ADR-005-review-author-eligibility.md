# ADR-005: 실제 이용 고객만 후기를 쓰게 하는 확인 절차

- **상태:** Accepted
- **날짜:** 2026-10-27
- **결정 책임자:** <미정>
- **관련 항목:** FR-013, FR-019, FR-021, FR-022, FR-025, FR-026, SCR-012, SCR-014, [ADR-003](ADR-003-fast-consultation-check.md)
- **대체 관계:** 없음

## 1. 배경 및 문제

지금은 카카오·네이버로 로그인한 회원이면 누구나 후기를 쓸 수 있고, 저장 즉시 공개된다(FR-013). 수업 후기(SCR-012)는 서비스 핵심 화면이고 홈에도 최신 후기가 노출되므로(SCR-001), 수업이나 무료체험을 받지 않은 사람이 쓴 후기가 섞이면 후기 전체의 신뢰가 떨어진다.

원하는 결과는 **수업을 받았거나 무료체험 등 서비스를 실제로 이용한 사람만 후기를 남길 수 있고, 방문자가 이를 믿을 수 있는 것**이다. 동시에 관리자(대표 1인) 운영 부담이 감당 가능한 수준이어야 한다.

## 2. 요구사항 및 제약 조건

### 확인된 사실
- `ReviewService.createReview`는 탈퇴하지 않은 회원인지(`getActiveMember`)만 확인하고 저장한다. 공개 전 검수나 이용 여부 확인이 없다.
- 후기 유형은 `FREE_TRIAL`(무료체험 후기)과 `CLASS`(수업 후기) 두 가지다(`ReviewType`). 무료체험만 받은 사람도 후기 작성 대상이다.
- 저장소에 수강·계약·결제·수업 일정 같은 "이용 이력" 도메인이 없다. 서버가 누가 서비스를 이용했는지 알 수 있는 데이터가 없다.
- 상담 신청(`Consultation`)은 비회원도 하고(FR-003), 회원과 연결되지 않으며 전화번호만 저장한다. 전화번호 인증을 하지 않는다(SCR-010, ADR-003).
- 상담 처리 상태 "상담 완료"(FR-026)는 상담이 끝났다는 뜻이지, 수업을 받았다는 뜻이 아니다.
- 기관 상담 신청(FR-001)의 연락처는 기관 담당자 번호다. 어린이집·유치원 수업을 받은 아이의 보호자는 상담 신청 기록에 나타나지 않는다.
- 회원 전화번호 저장(FR-019)은 엔티티에 필드만 있고 가입 정보 입력 화면(SCR-013)은 미구현이다.
- 관리자는 이미 회원별 권한을 바꾸는 화면이 있다(FR-022, 직원 지정·해제). 역할은 `MEMBER`/`STAFF`/`ADMIN` 하나만 가진다.
- 관리자는 후기를 숨기거나 다시 공개할 수 있다(FR-021). 사후 조치 수단은 이미 있다.

### 가정 및 가설
- 가정: 수업 계약·일정은 사이트 밖(전화, 메시지 등)에서 대표가 관리하며, 대표는 누가 이용 고객인지 알고 있다. 확인하지 않았다.
- 가정: 주력 사업이 어린이집·유치원 정기 수업(SCR-016)이므로, 후기를 쓸 사람의 상당수는 기관 수업을 받은 아이의 보호자일 수 있다. 비율은 모른다.
- 가정: 현재 운영. 환경의 실제 후기는 없거나 매우 적다(진행 문서에는 로컬 예시 후기만 기록). 운영 DB로 확인하지 않았다.
- 가설: 작성 전에 확인 절차를 하나 넣으면 후기 작성 수가 줄어든다. 얼마나 줄지는 측정하지 않았다

### 제약 조건 / 비목표
- 관리자는 대표 1인이다. 후기마다 수작업이 필요한 방식은 운영 부담이 된다.
- 비회원 상담 신청(FR-003)과 상담 신청 폼의 입력 부담은 바꾸지 않는다.
- 결제·수강 관리 시스템을 새로 만드는 것은 이번 결정의 범위가 아니다.
- 후기 내용의 진위(과장, 허위 내용)를 판단하는 것은 범위가 아니다. 이 ADR은 "누가 쓸 수 있는가"만 다룬다.
- 휴대전화 본인 인증(SMS 등) 같은 외부 유료 서비스 도입은 비용과 의존성 추가라 별도 확인이 필요하다.

## 3. 결정 요인

- **신뢰성(절대 제약에 가까움):** 이용하지 않은 사람이 우회해서 쓰기 어려워야 한다. 전화번호처럼 남이 쉽게 입력할 수 있는 값만으로 자격을 주면 안 된다.
- **이용 고객 범위(절대 제약):** 1:1 가정 방문 고객뿐 아니라 기관 수업을 받은 아이의 보호자, 무료체험 이용자도 쓸 수 있어야 한다.
- **운영 부담(중요):** 대표가 반복적으로 해야 하는 일이 적어야 한다.
- **작성 편의(선호):** 실제 고객이 후기를 쓰기까지의 단계가 적어야 한다.
- **개인정보(중요):** 확인을 위해 새로 모으거나 대조하는 개인정보가 적어야 한다.
- **구현·변경 비용(선호):** 현재 후기·회원 구조를 크게 바꾸지 않고, 나중에 더 강한 방식으로 바꿀 수 있어야 한다.
- **기존 후기 처리:** 도입 전에 쓰인 후기를 어떻게 다룰지 정해야 한다.

## 4. 검토한 대안

### 대안 A — 현상 유지 (누구나 작성, 사후 숨김)
- **접근 방식:** 지금처럼 로그인한 회원 누구나 작성하고 즉시 공개한다. 이용 고객이 아닌 후기는 관리자가 발견하면 숨긴다(FR-021).
- **장점:** 추가 구현이 없다. 실제 고객의 작성 단계가 가장 적다.
- **비용 및 위험:** 이용 여부를 막지 못하고, 관리자가 모든 후기를 보고 판단해야 한다. 숨기기 전까지는 공개되어 홈에도 노출된다. 방문자는 어떤 후기가 실제 고객 후기인지 구분할 수 없다.
- **적합한 경우:** 후기 수가 적고 대표가 매번 확인할 수 있으며, 허위 후기가 실제로 문제가 되지 않을 때.

### 대안 B — 관리자 승인 후 공개 (사전 검수)
- **접근 방식:** 누구나 작성할 수 있지만 저장 시 "검수 대기"로 두고, 관리자가 이용 고객임을 확인하고 승인하면 공개한다. 관리자 후기 관리 메뉴(SCR-014)에 대기 목록과 승인 버튼을 추가한다.
- **장점:** 공개되는 후기는 모두 관리자가 확인한 것이다. 회원 구조를 바꾸지 않는다. 기관 보호자·무료체험 이용자도 같은 방식으로 처리된다.
- **비용 및 위험:** 후기마다 관리자 작업이 생긴다. 작성자 이름이 회원 이름(소셜 계정 이름)이라, 대표가 그 이름만으로 실제 고객을 알아보기 어려울 수 있다(특히 기관 수업 보호자). 승인 전까지 작성자는 후기가 안 보이므로 안내가 필요하다. "저장 즉시 공개"(FR-013, SCR-012 안내 문구)를 바꿔야 한다.
- **적합한 경우:** 후기 수가 대표가 매번 검수할 수 있을 만큼 적고, 대표가 작성자를 식별할 수단(예: 작성 시 아이 이름·이용 기관 입력)이 있을 때.

### 대안 C — 관리자가 "이용 고객"으로 지정한 회원만 작성
- **접근 방식:** 직원 권한(FR-022)처럼 관리자가 회원 목록에서 특정 회원을 "이용 고객"으로 지정한다. 지정된 회원만 후기를 쓸 수 있다. 역할(`MemberRole`)은 하나만 가지므로, 직원이면서 고객인 경우를 고려해 역할이 아닌 별도 필드(예: 지정 시각)로 둔다.
- **장점:** 한 번 지정하면 그 회원은 이후 자유롭게 쓴다. 기존 관리자 회원 화면을 재사용할 수 있다. 공개 정책(즉시 공개)은 그대로 둘 수 있다.
- **비용 및 위험:** 고객이 먼저 가입해야 하고, 대표가 회원 목록에서 그 사람을 찾아 지정해야 한다. 회원 전화번호가 아직 수집되지 않아(FR-019 미구현) 이름만으로 찾게 되며 동명이인 구분이 어렵다. 기관 수업 보호자처럼 대표가 개별로 모르는 고객은 지정이 어렵다. 이용이 끝난 뒤 자격을 회수할지 정해야 한다.
- **적합한 경우:** 이용 고객 대부분이 1:1 가정 방문처럼 대표가 개인을 아는 고객이고, 회원 전화번호 수집(FR-019)이 먼저 구현될 때.

### 대안 D — 후기 작성 코드 발급 (초대 코드·링크)
- **접근 방식:** 관리자가 관리자 화면에서 후기 작성 코드(또는 코드가 담긴 링크)를 발급해 이용 고객에게 전달한다. 회원은 후기 작성 시 코드를 입력하고, 서버는 유효한 코드인지 확인한 뒤 사용 처리한다. 코드는 1회용(1:1 고객)이나 사용 횟수·기간 제한이 있는 묶음 코드(기관 수업 보호자에게 기관을 통해 배포)로 나눌 수 있다. 코드에 유형(무료체험/수업)을 묶을 수도 있다.
- **장점:** 대표가 고객 개인을 알지 못해도 기관을 통해 보호자에게 전달할 수 있다. 관리자 작업이 "후기마다"가 아니라 "고객 또는 기관마다 한 번"이다. 공개 정책은 즉시 공개를 유지할 수 있다. 새로 모으는 개인정보가 없다.
- **비용 및 위험:** 코드 테이블, 발급·목록·폐기 API와 관리자 화면, 작성 화면의 코드 입력 단계가 필요하다. 코드가 유출되면 이용하지 않은 사람도 쓸 수 있다(묶음 코드는 특히). 사용 횟수·만료로 피해 범위를 줄여야 한다. 실제 고객의 작성 단계가 하나 늘어난다.
- **적합한 경우:** 기관 수업 보호자를 포함해야 하고, 대표가 수업 종료·체험 직후 코드를 전달하는 운영 습관을 만들 수 있을 때.

### 대안 E — 상담 신청 전화번호와 회원 전화번호 자동 대조
- **접근 방식:** 회원 전화번호(FR-019)와 처리 상태가 특정 단계인 상담 신청(FR-026)의 전화번호가 같으면 작성 자격을 준다.
- **장점:** 관리자 작업 없이 자동으로 판단한다.
- **비용 및 위험:** 상담 신청과 회원 전화번호 모두 인증하지 않아, 남의 번호를 입력하면 우회된다. 상담 완료는 수강을 뜻하지 않는다. 기관 신청은 담당자 번호라 보호자를 찾을 수 없다. 우회를 막으려면 휴대전화 본인 인증이 필요해 외부 서비스·비용이 추가된다. 상담 신청 개인정보를 원래 수집 목적(상담 연락) 밖에서 쓰게 된다.
- **적합한 경우:** 휴대전화 본인 인증을 도입하고, 이용 고객 대부분이 개인 상담 신청을 거친 1:1 고객일 때. 현재 조건에는 맞지 않는다.

### 대안 F — 수강·이용 이력 도메인 도입
- **접근 방식:** 수강 계약(고객, 프로그램, 기간)이나 무료체험 이력을 사이트에서 관리하고, 이력이 있는 회원만 후기를 쓰게 한다.
- **장점:** 가장 정확하고, 후기에 "어떤 프로그램 이용"을 붙이는 등 확장이 쉽다.
- **비용 및 위험:** 현재 사이트 밖에서 하는 운영 업무를 사이트로 옮겨야 하고 구현 범위가 크다. 기관 수업 보호자는 여전히 계약 당사자가 아니라 별도 연결 수단이 필요하다. 후기 자격 하나를 위해 들이기엔 범위가 넓다.
- **적합한 경우:** 수강·일정·결제 관리를 사이트에서 하기로 별도로 결정했을 때.

## 5. 결정

- **선택한 대안:** 대안 D — 후기 작성 코드 발급. 대안 A의 사후 숨김(FR-021)은 그대로 유지해 2차 확인 수단으로 쓴다.
- **근거:**
  - 비정상적인 후기 작성(서비스를 이용하지 않은 사람의 후기)을 최소한으로, 적은 비용으로 막는다. 코드가 없으면 후기를 쓸 수 없어 "로그인만 하면 누구나" 상태를 바로 끝낸다.
  - 관리자 작업이 "후기마다"가 아니라 "고객 또는 기관마다 한 번"이라 대표 1인 운영에 맞는다(결정 요인: 운영 부담).
  - 기관을 통해 보호자에게 코드를 전달할 수 있어, 대표가 개인을 모르는 기관 수업 보호자와 무료체험 이용자도 포함된다(결정 요인: 이용 고객 범위).
  - 새로 모으는 개인정보가 없고, 즉시 공개 정책을 유지할 수 있다.
  - 코드가 유출되는 경우는 기존 숨김 기능(FR-021)으로 사후에 걸러 낸다. 사전 차단(코드)과 사후 숨김을 함께 두는 이중 확인이다.
- **다른 대안을 선택하지 않은 이유:**
  - A(현상 유지)만으로는 비이용자 후기를 막지 못하고, 숨기기 전까지 공개·홈 노출된다. 숨김 기능만 보조 수단으로 남긴다.
  - B(사전 검수)는 후기마다 관리자 작업이 생기고, 소셜 계정 이름만으로 작성자를 알아보기 어렵다.
  - C(이용 고객 지정)는 회원 전화번호 수집(FR-019)이 미구현이라 회원을 찾기 어렵고, 기관 수업 보호자를 지정하기 어렵다.
  - E(전화번호 대조)는 번호 인증이 없어 우회되고, 상담 신청 개인정보를 목적 밖에서 쓰게 된다.
  - F(이용 이력 도메인)는 후기 자격 하나를 위해 들이기에는 구현 범위가 크다.

## 6. 결과

### 기대 효과
- 작성 코드를 받은 사람만 후기를 쓸 수 있어, 비이용자가 로그인만으로 후기를 쓰는 경로가 막힌다.
- 공개 정책(저장 즉시 공개)은 유지되어 실제 고객의 후기가 바로 보인다.
- 코드가 유출되어 들어온 후기는 관리자가 숨김(FR-021)으로 처리할 수 있다.

### 감수하는 트레이드오프 / 위험
- 코드가 유출되면 비이용자도 쓸 수 있다. 특히 기관에 배포하는 묶음 코드는 위험이 크다. 사용 횟수·만료 기간으로 피해 범위를 줄이고, 남는 위험은 사후 숨김으로 처리한다.
- 실제 고객의 작성 단계가 하나(코드 입력) 늘어난다. 링크에 코드를 담아 전달하면 줄일 수 있다.
- 대표가 수업 종료·체험 직후 코드를 전달하는 운영 습관이 필요하다.
- 구현 범위: 코드 저장(테이블), 발급·목록·폐기 API, 관리자 화면 메뉴, 작성 화면의 코드 입력·검증.

### 후속 작업
- 코드 종류와 기본값 결정: 1회용 코드(1:1 고객)와 묶음 코드(기관)의 사용 횟수·만료 기간, 코드에 후기 유형(무료체험/수업)을 묶을지.
- 링크로 전달할 때의 흐름: 링크를 열면 로그인 후 코드가 자동으로 채워지는지.
- 도입 전에 쓰인 후기 처리 방식 결정: 그대로 두기 / 관리자가 확인 후 숨기기 / "이용 확인 전 후기" 구분 표시.
- FR-013 수정("인증된 회원 누구나" → 유효한 작성 코드를 가진 회원), 코드 발급·검증 FR 신규, SCR-012 작성 화면 코드 입력·비자격 안내, SCR-014 코드 발급 메뉴 추가. `docs/requirements/requirement_homepage.md`(미결 "후기 작성 권한" 정리 포함), `docs/progress.md` 갱신.
- 코드가 없거나 잘못된 경우의 화면 흐름과 오류 코드 정의(`back/docs/api-guidelines.md` 기준).
- 후기 수정(FR-025)에도 코드를 다시 확인할지 결정(기본안: 작성 시 1회만 확인).

## 7. 검증 계획

- 대표에게 확인: 수업 종료나 체험 직후 고객·기관에 코드를 전달할 접점이 있는지, 기관에 묶음 코드를 배포할 수 있는지.
- 운영 DB에서 `review` 건수와 작성 회원 수를 조회해 기존 후기 처리 범위를 확인한다.
- 실제 고객 몇 명에게 코드 입력(또는 링크) 작성 흐름을 써 보게 하고 막히는 단계를 관찰한다.
- 도입 후 일정 기간 동안 관리자가 숨김 처리(FR-021)한 후기 수와, 그중 묶음 코드로 쓰인 후기 수를 확인해 코드 유출 여부를 점검한다.

## 8. 재검토 조건

- 수강·일정·결제 관리를 사이트에서 하기로 결정할 때(대안 F 재검토).
- 휴대전화 본인 인증을 다른 목적으로 도입할 때(대안 E 재검토).
- 후기 작성 코드 유출 등으로 비이용자 후기가 반복해서 발견될 때.
- 후기 수가 늘어 관리자 수작업(대안 B·C)을 감당할 수 없을 때.
- 확인 절차 때문에 실제 고객의 후기 작성이 눈에 띄게 줄었다는 관찰이 있을 때.
