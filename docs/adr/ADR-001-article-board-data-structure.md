# ADR-001: 수업 현장 게시물과 몽키즈 연구소 글의 데이터 구조

- **상태:** Proposed
- **날짜:** 2026-10-21
- **결정 책임자:** <미정>
- **관련 항목:** FR-008, FR-009, FR-010, FR-011, FR-012, FR-024 / SCR-006, SCR-015, SCR-024 / PR #22, #23 (커밋 `dbad11b`)
- **대체 관계:** 없음

## 1. 배경 및 문제

직원이 쓰는 글은 수업 현장 게시물(SCR-006)과 몽키즈 연구소 글(SCR-024) 두 종류입니다. 두 글은 제목, HTML 본문, 본문 속 사진, 작성 권한, 공감을 공통으로 갖습니다. 하지만 기능은 이미 갈라지고 있습니다. 댓글은 수업 현장 글만 받고, 비로그인 열람 제한은 수업 현장 글에만 있습니다.

원하는 결과는 두 가지입니다.

1. 한 종류의 글에 기능을 더하거나 바꿀 때 다른 종류에 영향이 없다.
2. "연구소 글에는 댓글이 없다", "분류는 자기 묶음 안에서만 고른다" 같은 규칙을 가능한 한 DB가 보장한다.

2026-10-20에 공통 부모 + 테이블 분리 구조를 구현했지만(PR #22, #23), 다른 구조와 비교한 기록은 없습니다. 이 ADR은 그 비교를 남기고 어떤 구조를 쓸지 정합니다.

## 2. 요구사항 및 제약 조건

### 확인된 사실
- FR-008: 두 묶음은 공통 구조를 공유하되 저장(`post`, `lab_post`)과 API(`/api/v1/posts`, `/api/v1/lab-posts`)를 분리하고, 사진 업로드 URL 발급은 함께 쓴다 (사용자 결정 2026-10-20).
- FR-009: 작성·수정·삭제 권한 규칙은 두 글이 같다.
- FR-010, FR-011: 댓글은 수업 현장 글에만 있고, 공감은 두 글 모두 받는다.
- FR-012: 비로그인 열람 제한(최초 4개)은 수업 현장 글에만 적용된다.
- FR-024: 제목 검색은 연구소 목록에만 구현됐다.
- 현재 구조: 공통 필드는 `@MappedSuperclass`(`Article`, `ArticleImage`)로 코드만 공유한다. 테이블은 `post`·`post_image`·`post_like`·`post_comment`와 `lab_post`·`lab_post_image`·`lab_post_like`로 나뉜다 (`back/docs/schema.md`).
- 분류는 묶음마다 다른 enum이고, DB에는 분류 값에 대한 CHECK 제약이 없다. 분류 값을 추가할 때 DDL을 바꾸지 않으려고 enum 컬럼을 `varchar`로 두는 것이 스키마 규칙이다 (`back/docs/schema.md` 1절).
- DB는 MariaDB다 (`mariadb-java-client`, `back/docs/database.md`). 운영 버전은 확인하지 않았다.
- 두 글의 사진 키는 같은 접두사(`posts/`)를 쓴다. 저장할 때는 접두사와 S3에 파일이 있는지만 확인하고, 그 키를 이 글을 위해 발급했는지(소유)는 검사하지 않는다. `image_key`에 UNIQUE 제약도 없다. 따라서 같은 묶음이든 다른 묶음이든 두 글이 같은 키를 참조할 수 있다.
- 사진 URL은 공개 주소 + 키라서 키를 URL에서 알 수 있다. 작성은 직원만 할 수 있다 (FR-009).
- 현재 S3 사진을 지우는 기능은 없다. 글 삭제는 소프트 삭제(`deleted_at`)만 한다.
- 글을 수정하면 사진 행을 모두 지우고 본문 순서대로 다시 넣는다 (`clearImages()` 후 `addImage`).
- 두 테이블의 `id`는 각자 증가하므로 값이 겹칠 수 있다. 화면 경로와 API가 나뉘어 있어 지금은 문제가 없다.
- 운영 환경은 스키마 자동 변경을 하지 않고 마이그레이션 도구도 없다. 구조를 바꾸려면 DDL을 손으로 적용해야 한다.

### 가정 및 가설
- 가정: 운영 DB의 글 수는 아직 많지 않다. 실제 건수는 확인하지 않았다.
- 가정: 두 묶음을 섞어 보여 주는 화면(통합 최신글, 통합 검색)은 가까운 시일 안에 생기지 않는다. 지금 요구사항에는 없다.
- 가정: 두 글의 주 독자가 다르다. 요구사항에 명시되어 있지 않다.
- 가설: 두 글의 차이는 앞으로도 기능 유무(댓글, 열람 제한 등) 수준이고, 공통 컬럼은 크게 늘지 않는다.
- 가설: 한 글의 본문을 다른 글 편집기로 복사해 붙이면 `data-image-key`가 따라와 같은 키를 참조하게 될 수 있다. 응답 HTML과 편집기 동작을 확인하지 않았다.
- 가설: Hibernate는 orphan 삭제보다 INSERT를 먼저 실행하므로, 사진 테이블에 `image_key` UNIQUE를 걸면 같은 사진을 유지하는 수정이 제약 위반으로 실패한다. 테스트로 확인하지 않았다.

### 제약 조건 / 비목표
- API 경로와 화면 구조는 범위가 아니다 (FR-008에서 분리로 정해짐).
- 사진 저장소(S3)와 업로드 URL 발급 방식은 바꾸지 않는다.
- 세 번째 글 종류를 미리 대비한 일반화는 목표가 아니다.

## 3. 결정 요인

- **도메인 책임과 생명주기:** 두 글은 쓰는 사람과 권한은 같지만, 받는 상호작용(댓글, 열람 제한)이 다르다. 기능이 따로 자라는 것을 구조가 막지 않아야 한다. 핵심 요인이다.
- **데이터 무결성과 제약 조건:** 연구소 글의 댓글, 다른 묶음의 분류 같은 잘못된 상태를 DB 제약으로 막을 수 있어야 한다. 앱 검사로만 막는 것은 차선이다. 핵심 요인이다.
- **쿼리/접근 패턴과 성능:** 현재 쿼리는 모두 "한 묶음 안에서 분류별 최신순 + 페이지"이고, 묶음을 넘는 쿼리는 없다. 선호 사항이다.
- **변경 용이성과 마이그레이션:** 공통 규칙을 바꿀 때 고칠 곳이 적어야 한다(선호). 마이그레이션 도구가 없어 구조를 바꾸는 비용이 크다(제약에 가까움).
- **보안과 운영:** 사진 키의 소유를 검사하지 않으므로 두 글이 같은 키를 참조할 수 있다. 지금은 S3 삭제가 없어 피해가 없지만, 글 삭제·수정 때 사진을 정리하는 기능을 넣으면 한 글의 정리가 같은 키를 쓰는 다른 글의 사진을 지운다. 구조와 무관한 근본 원인이라 어느 대안에서든 막아야 한다. 구조에 따라 달라지는 것은 정리 기능이 확인해야 할 테이블 수다.
- **개발 기간과 복잡도:** 팀이 JPA 매핑과 쿼리를 쉽게 읽고 고칠 수 있어야 한다. 선호 사항이다.

## 4. 검토한 대안

### 대안 A — 현상 유지: 공통 부모 클래스 + 묶음별 테이블
- **접근 방식:** 공통 필드와 쓰기 규칙은 코드로 공유하고, 글·사진·공감 테이블은 묶음마다 둔다. 댓글 테이블은 수업 현장 쪽에만 둔다.
- **장점:** 댓글 FK가 `post`만 가리켜 연구소 글 댓글을 DB가 막는다. 한쪽 전용 컬럼(`comment_count` 등)과 인덱스를 다른 쪽에 영향 없이 둘 수 있다. 이미 구현·테스트됐고 마이그레이션 비용이 없다.
- **비용 및 위험:** 사진·공감 테이블과 Entity가 두 벌이라, 공통 컬럼을 바꾸면 DDL을 두 번 적용해야 한다. 묶음을 섞는 목록이 생기면 `UNION`이나 두 번 조회가 필요하다. 분류 조합은 앱의 enum 매핑으로만 보장된다. 두 사진 테이블이 같은 사진 키 공간(`posts/`)을 공유하므로, 키 경로만 보고는 어느 테이블의 사진인지 알 수 없다. 사진 정리 기능은 반드시 두 테이블을 모두 확인해야 하고, 하나라도 빠뜨리면 다른 묶음의 사진이 지워진다. 예: `posts/` 아래에서 `post_image`에 없는 키를 고아로 보고 지우면, `lab_post_image`의 사진이 모두 지워진다.
- **되돌리는 비용:** 바꿀 것이 없다. 나중에 C로 옮길 때는 공통 컬럼을 `article`로 올리고 두 테이블의 행을 옮겨야 한다. 두 테이블의 `id`가 겹치므로 새 ID를 매기고 사진·공감·댓글의 FK를 다시 연결해야 한다.
- **적합한 경우:** 두 글이 따로 조회되고 기능 차이가 계속 커지는 경우.

### 대안 B — 단일 테이블 + 묶음 구분 컬럼
- **접근 방식:** `post` 하나에 묶음 구분 컬럼을 두고(JPA `SINGLE_TABLE` 또는 일반 컬럼), 분류 enum을 합친다. 사진·공감·댓글 테이블은 하나씩만 둔다.
- **장점:** 테이블과 Entity가 가장 적어 공통 변경은 한 곳만 고친다. 묶음을 섞는 목록·검색이 쿼리 하나로 된다. 글 ID가 겹치지 않는다.
- **비용 및 위험:** 연구소 글 댓글을 FK로 막을 수 없어 앱 검사나 트리거가 필요하다. 묶음과 분류의 조합을 막으려면 CHECK 제약이 필요하다(MariaDB 10.2.1 이상에서 적용, 운영 버전 미확인). 그러면 분류 값을 추가할 때마다 DDL을 바꿔야 해서 `varchar` 스키마 규칙과 충돌한다. 한쪽 전용 컬럼이 늘수록 다른 쪽에 의미 없는 컬럼이 쌓인다. FR-008의 저장 분리 결정을 다시 정해야 하고, `lab_post` 계열 데이터를 옮겨야 한다.
- **되돌리는 비용:** 다시 나누려면 구분 컬럼으로 행을 골라 테이블을 쪼개고, 공용 사진·공감·댓글 행도 묶음별로 나눠야 한다. A에서 B로 가는 비용과 비슷하거나 더 클 것으로 본다 (가정).
- **적합한 경우:** 두 글의 차이가 분류 이름 정도로 작고, 섞어 보여 주는 화면이 중요한 경우.

### 대안 C — 조인 상속: 공통 `article` 테이블 + 묶음별 확장 테이블
- **접근 방식:** 공통 컬럼은 `article`에, 전용 컬럼은 `post`·`lab_post`(PK가 곧 `article` FK)에 둔다(JPA `JOINED`). 사진·공감은 `article`을 가리키는 공용 테이블 하나씩, 댓글은 `post`를 가리킨다.
- **장점:** 댓글이 `post`만 가리켜 DB가 막는다. 사진·공감 테이블의 중복이 없고, 묶음을 섞는 조회는 `article`만 보면 된다.
- **비용 및 위험:** 공용 사진·공감 테이블은 묶음을 FK로 구분하지 못해, 한쪽만 공감을 없애면 다시 앱 검사가 필요하다. `article` 하나에 확장 행이 정확히 하나인지는 DB가 보장하지 못한다. 조회·저장마다 조인이 하나 는다. 분류를 둘 곳은 둘 중 하나다. 확장 테이블에 두면 분류 무결성은 A와 같지만 "분류별 최신순" 인덱스를 `created_at`과 한 테이블에 둘 수 없다. `article`에 두면 인덱스는 되지만 분류 무결성은 B와 같아진다. 테이블을 새로 만들고 데이터를 옮겨야 해서 마이그레이션 비용이 가장 크다.
- **되돌리는 비용:** A로 돌아가려면 `article`과 확장 테이블을 합쳐 묶음별 테이블로 펼치고, 공용 사진·공감 테이블을 다시 둘로 나눠야 한다. 비용은 C로 오는 것과 비슷할 것으로 본다 (가정).
- **적합한 경우:** 공통 컬럼이 많고, 묶음을 섞는 조회와 묶음별 확장이 둘 다 자주 필요한 경우.

### 함께 검토했지만 대안으로 두지 않은 변형
- **다형 연관:** 사진·공감 테이블을 하나로 두고 `target_type` + `target_id`로 글을 가리킨다. 테이블 중복은 줄지만 `target_id`에 FK를 걸 수 없어, 지워진 글이나 다른 묶음 글을 가리키는 행을 DB가 막지 못한다. 핵심 요인인 데이터 무결성을 가장 약하게 만족해서 제외했다.

### 후속 작업

  - 업로드 URL을 발급할 때 키를 발급 기록으로 남기고, 저장할 때 한 글에서 한 번만 쓸 수 있게 한다.

## 7. 검증 계획

`decide` 전에 할 것:
- 운영 DB의 `post`, `lab_post` 행 수를 확인해 B·C의 마이그레이션 비용을 가늠한다.
- 같은 사진 키로 수업 현장 글과 연구소 글을 각각 저장하는 통합 테스트를 만들어, 현재 구조에서 실제로 저장되는지 확인한다.

B를 검토한다면 `decide` 전에 할 것:
- 운영 MariaDB 버전을 확인해 CHECK 제약을 쓸 수 있는지 본다.
- 분류별 최신순 목록과 상세 조회의 쿼리 플랜(`EXPLAIN`)을 현재 구조와 비교한다. C도 같다.

`decide` 후에 할 것:
- 사진 테이블에 `image_key` UNIQUE를 걸고 같은 사진을 유지한 채 글을 수정하는 테스트로, Hibernate 실행 순서 가설을 확인한다.

## 8. 재검토 조건

- 두 묶음을 섞어 보여 주는 화면(홈 통합 최신글, 통합 검색 등)이 요구사항에 들어올 때.
- 세 번째 글 종류가 생길 때.
- 공통 컬럼 변경이 잦아져 두 테이블의 DDL을 함께 고치는 일이 반복될 때.
- 한쪽 묶음에서만 공감을 없애거나 댓글을 더하는 등 기능 차이가 바뀔 때.
