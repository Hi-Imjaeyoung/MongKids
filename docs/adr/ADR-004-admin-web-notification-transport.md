# ADR-004: 관리자가 웹에서 새 상담 알림을 받는 방법 (폴링, SSE, 웹소켓)

- **상태:** Accepted
- **날짜:** 2026-10-26
- **결정 책임자:** 저장소 관리자 (사용자)
- **관련 항목:** FR-005, FR-026, SCR-014 / [ADR-003](ADR-003-fast-consultation-check.md) (대안 B 후속) / 이슈 #46
- **대체 관계:** 없음

## 1. 배경 및 문제

[ADR-003](ADR-003-fast-consultation-check.md)에서 사이트 안 신규 건수 표시(대안 B)를 정했습니다. 관리자가 로그인해 있으면 헤더 "관리자" 링크와 상담 신청 메뉴에 처리하지 않은(`RECEIVED`) 상담 건수가 보입니다. 이 ADR은 그다음 문제를 다룹니다. 화면을 열어 둔 관리자에게 새 신청이 생겼다는 사실을 어떻게 전달할지입니다.

원하는 결과는 세 가지입니다.

1. 관리자가 사이트를 열어 둔 동안 새 신청이 들어오면, 새로고침하지 않아도 건수가 바뀐다.
2. 관리자가 처리 상태를 바꾸면 건수가 바로 맞춰진다.
3. 지금 운영 구성(EC2 한 대, CloudFront, Caddy)과 MVP 일정 안에서 안정적으로 동작한다.

ADR-003의 근거인 "인증 없는 신청이 몰려도 관리자 알림 부하가 늘지 않게"와 "최소 기능 단위로 먼저 구현한 뒤 리팩토링"이 이 결정에도 그대로 적용됩니다.

## 2. 요구사항 및 제약 조건

### 확인된 사실
- 백엔드는 Spring Boot 서블릿 스택(`spring-boot-starter-webmvc`, 내장 Tomcat)입니다. WebFlux, WebSocket 의존성, `@Async`, `@Scheduled`, `@TransactionalEventListener` 사용처가 없습니다 (`back/build.gradle`).
- 요청 경로는 브라우저 → CloudFront(`mongkiz.com`, `/api/*` 동작) → Caddy(`origin.mongkiz.com`, EC2) → Spring Boot `127.0.0.1:8080`입니다 (`docs/deploy-checklist.md`, `back/deploy/Caddyfile`).
- CloudFront의 백엔드 동작은 `CachingDisabled`입니다. 쿠키·쿼리·헤더를 전부 넘기고, 허용 메서드는 GET~DELETE입니다. 오리진 읽기 제한 시간 등 타임아웃 값은 문서에 기록되어 있지 않습니다.
- 백엔드는 EC2 한 대(t4g.small)에서 돕니다. 여러 대로 늘리는 구성은 없습니다.
- 인증은 같은 도메인의 JWT 쿠키로 합니다. 프론트 `client.js`는 상대 경로와 `credentials: 'same-origin'`을 씁니다. 로컬에서는 Vite 프록시가 `/api`를 백엔드로 넘깁니다.
- 관리자 권한은 `MemberService.validateAdmin`이 요청마다 DB의 현재 역할로 검사합니다.
- 처리 상태로 거르는 조회에는 인덱스 `idx_consultation_status_created_at`가 있습니다.
- JWT 인증 필터(`JwtAuthenticationFilter`)는 토큰의 `role` 클레임만 읽고 DB는 조회하지 않습니다. DB 조회는 `validateAdmin`에서 일어납니다(회원 PK 조회 1회).
- `spring.jpa.open-in-view: false`입니다. 요청이 길게 열려 있어도 서비스 트랜잭션이 끝나면 DB 커넥션을 돌려줍니다. 커넥션 풀은 따로 설정하지 않아 HikariCP 기본값을 씁니다.
- 처리 상태 인덱스는 `(status, created_at)` 순서입니다. 따라서 `status = 'RECEIVED'` 건수 조회는 인덱스 앞부분 범위만 읽습니다. 상담은 JOINED 상속이지만 `status`가 부모 테이블 `consultation`에 있어 조인이 필요 없습니다.
- 관리자(ADMIN)의 역할은 관리자 화면에서 바꿀 수 없습니다(`M003`, FR-022).
- 목표 지연은 "즉시"입니다(사용자 결정 2026-10-26). 허용할 초 수는 정하지 않았습니다.
- 관리자는 대표 한 명입니다. 직원(STAFF)은 관리자 화면에 들어갈 수 없습니다(FR-022).

### 가정 및 가설
- 가정: 동시에 화면을 열어 두는 관리자는 1~2명, 탭은 몇 개 수준입니다. 측정하지 않았습니다.
- 가정: 상담 신청은 하루에 몇 건 수준입니다. 측정하지 않았습니다.
- 가설: CloudFront는 오리진의 응답을 일정 시간 받지 못하면 연결을 끊습니다(오리진 응답·유지 제한 시간, 기본값은 수십 초 수준으로 알려져 있음). 따라서 SSE를 쓰려면 그보다 짧은 주기로 하트비트를 보내야 합니다. 외부 문서 기준이며 운영 배포 설정 확인이 필요합니다.
- 가설: CloudFront와 Caddy 모두 WebSocket 업그레이드를 넘깁니다. Caddy는 `text/event-stream` 응답을 버퍼링 없이 바로 흘려보냅니다. 외부 문서 기준이며 확인이 필요합니다.
- 가설: Tomcat 비동기 처리(`SseEmitter`)는 대기 중에 요청 스레드를 붙잡지 않습니다. 다만 연결과 메모리는 열린 연결 수만큼 쓰입니다.

### 제약 조건 / 비목표
- 사이트 밖 알림(메일·푸시·메시지)은 범위가 아닙니다(ADR-003).
- 전달하는 내용은 건수 또는 "변경 있음" 신호로 한정합니다. 신청자 개인정보는 실시간 채널로 보내지 않습니다.
- 백엔드를 여러 대로 늘리는 것은 지금 계획에 없습니다. 다만 늘릴 때 바꿔야 하는 범위는 기록합니다.
- 새 의존성 추가와 설정 변경(CloudFront, Caddy)은 사용자 확인 후 진행합니다.

## 3. 결정 요인

- **운영 경로 호환성 (절대 제약):** CloudFront → Caddy → Tomcat을 거쳐 운영에서 실제로 동작해야 합니다. 운영 설정을 바꿔야 한다면 그 범위가 명확해야 합니다.
- **지연 (요구사항):** 목표는 "즉시"입니다(사용자 결정 2026-10-26). 허용 초 수가 정해지지 않아 B의 폴링 주기가 이 요구를 만족하는지는 아직 판정할 수 없습니다.
- **알림 부하와 서버 자원:** 신청이 몰리거나 관리자가 탭을 오래 열어 둘 때 늘어나는 요청 수, 열린 연결 수, DB 조회 수입니다. ADR-003의 근거와 이어지는 선호 사항입니다.
- **구현·테스트 복잡도:** MVP 마감(2026-11-11) 안에 기존 패턴(관리자 API, `validateAdmin`, MockMvc 통합 테스트)으로 만들고 검증할 수 있는지입니다.
- **인증과 보안:** 연결 중에 관리자 권한이 회수되거나 로그아웃할 때, 쿠키 기반 인증이 그대로 통하는지입니다.
- **확장과 되돌리기 비용:** 백엔드를 여러 대로 늘리거나 다른 방식으로 바꿀 때 다시 짜야 하는 범위입니다.

## 4. 검토한 대안

### 대안 A — 들어올 때만 조회 (주기 갱신 없음)
- **접근 방식:** 건수 API를 두고, 관리자 화면 진입, 페이지 이동, 처리 상태 변경 때만 다시 조회합니다.
- **장점:** 가장 단순합니다. 요청이 가장 적고 새 의존성이 없습니다.
- **비용 및 위험:** 화면을 열어 둔 채로는 새 신청이 보이지 않아 원하는 결과 1을 충족하지 못합니다. FR-005의 "로그인해 있는 동안 주기적으로 갱신"과도 맞지 않습니다.
- **적합한 경우:** 관리자가 화면을 오래 열어 두지 않고, 들어올 때 확인하는 것으로 충분할 때.

### 대안 B — 폴링 (주기적 조회)
- **접근 방식:** 대안 A에 더해, 관리자가 로그인해 있고 탭이 보이는 동안 일정 주기로 `GET` 건수 API를 부릅니다. 탭이 가려지면 멈추고, 다시 보이면 바로 한 번 조회합니다(`visibilitychange`).
- **장점:** 기존 REST·쿠키 인증·`validateAdmin`·MockMvc 테스트 패턴을 그대로 씁니다. CloudFront, Caddy 설정 변경이 필요 없습니다. 상태가 없어서 서버 재시작이나 여러 대 구성에도 그대로 동작합니다. 신청이 몰려도 요청 수는 주기에만 비례하므로 신청 수와 무관합니다.
- **비용 및 위험:** 지연은 최대 폴링 주기만큼입니다. 변화가 없어도 요청과 DB `count`가 주기마다 발생합니다. 인덱스가 있고 관리자 수가 적어 부담은 작을 것으로 예상하지만 측정하지는 않았습니다. 주기를 짧게 할수록 요청이 선형으로 늘어납니다.
- **적합한 경우:** 목표 지연이 수십 초~분 단위이고, 관리자 수가 적을 때.

### 대안 C — SSE (Server-Sent Events)
- **접근 방식:** 관리자 브라우저가 `EventSource`로 `GET /api/v1/admin/.../stream`에 연결을 유지합니다. 서버는 Spring MVC `SseEmitter`를 메모리에 보관합니다. 신청 저장이나 처리 상태 변경이 커밋되면(`@TransactionalEventListener(AFTER_COMMIT)`) 새 건수를 보냅니다. 연결이 끊기면 `EventSource`가 다시 연결합니다.
- **장점:** 새 의존성 없이 서블릿 스택만으로 만들 수 있습니다. 변화가 있을 때만 보내므로 지연이 짧고 쓸데없는 조회가 없습니다. 같은 출처 GET이라 쿠키 인증이 그대로 통합니다. 서버 → 브라우저 한 방향이라는 요구와 맞습니다.
- **비용 및 위험:**
  - CloudFront 연결 제한 시간보다 짧은 주기로 하트비트를 보내야 합니다. 운영에서 끊김·재연결 동작을 확인해야 합니다(가설).
  - 신청이 몰리면 그만큼 이벤트가 나갑니다. 묶어 보내기(디바운스)를 넣지 않으면 ADR-003이 피하려던 알림 부하가 사이트 안에서 다시 생길 수 있습니다.
  - 열린 연결을 메모리에 들고 있으므로, 백엔드를 여러 대로 늘리면 인스턴스 간 전달(Redis pub/sub 등)이 필요합니다. 재배포 때는 모든 연결이 끊겼다가 다시 연결됩니다.
  - 연결 중 권한이 회수되거나 로그아웃해도 연결은 남습니다. 끊어 주는 처리가 따로 필요합니다.
  - 비동기 응답이라 MockMvc 테스트가 일반 API보다 까다롭습니다.
- **적합한 경우:** 목표 지연이 수 초 단위이고, 운영 경로에서 SSE 동작을 확인할 시간이 있을 때.

### 대안 D — 웹소켓 (WebSocket, 필요하면 STOMP)
- **접근 방식:** `spring-boot-starter-websocket`을 추가하고 관리자 전용 엔드포인트로 양방향 연결을 엽니다. 신청 커밋 후 건수를 보냅니다.
- **장점:** 지연이 짧습니다. 나중에 양방향 기능(관리자 간 실시간 협업, 채팅 등)이 생기면 확장할 수 있습니다.
- **비용 및 위험:**
  - 새 의존성과 설정이 필요합니다. 핸드셰이크 인증(JWT 쿠키), Origin 검사, Spring Security 연동, 하트비트를 새로 구성해야 합니다.
  - CloudFront·Caddy의 업그레이드 전달과 유휴 시간 제한을 확인해야 합니다(가설).
  - 여러 대 확장 시 브로커가 필요합니다.
  - 지금 요구는 서버 → 브라우저 한 방향 건수 전달뿐이라 양방향 능력을 쓰지 않습니다. 세 방식 중 구현·테스트 부담이 가장 큽니다.
- **적합한 경우:** 양방향 실시간 기능이 요구사항에 생겼을 때.

| 운영 경로 호환 | 변경 없음 | 변경 없음 | 하트비트·제한 시간 확인 필요 | 업그레이드·유휴 시간 확인 필요 |
| 지연 | 다음 진입까지 | 최대 폴링 주기 | 커밋 직후(짧음) | 커밋 직후(짧음) |
| 신청이 몰릴 때 | 영향 없음 | 영향 없음(주기에만 비례) | 이벤트 수만큼 전송, 디바운스 필요 | C와 같음 |
| 서버 자원 | 최소 | 주기마다 요청 + `count` | 탭마다 연결 1개 유지 | 탭마다 연결 1개 유지 |

### B(1분 이내 지속 폴링)와 C(SSE)의 자원 비교

기호: `T` = 관리자 화면을 열어 둔 탭 수, `P` = 폴링 주기(초, 60 이하), `E` = 건수가 바뀌는 사건 수(신청 저장 + 처리 상태 변경), `H` = SSE 하트비트 주기(초), `R` = SSE 재연결 수. 아래 값은 모두 식에서 나온 것이며, 지연·처리 시간은 측정하지 않았습니다.

| 관점 | B 폴링 (`P` ≤ 60초) | C SSE |
|---|---|---|
| **DB 조회** | 요청마다 회원 PK 조회 1회(`validateAdmin`) + `RECEIVED` 건수 1회. 시간당 `2 × T × 3600 / P`회. 변화가 없어도 일정하게 발생 | 연결·재연결 때 권한 확인 + 초기 건수(`2 × R`회). 그 뒤에는 사건마다 건수 1회를 계산해 모든 탭에 보냄(`E`회, 탭 수와 무관) |
| **DB 커넥션** | 요청마다 짧게 빌렸다 반환. OSIV가 꺼져 있어 풀 점유는 쿼리 시간뿐 | 연결 중에는 DB 커넥션을 잡지 않음(OSIV 꺼짐). 이벤트 전송은 커밋 뒤(`AFTER_COMMIT`)에 별도 조회로 처리해야 함 |
| **신청이 몰릴 때** | 영향 없음. DB 부하는 `T`, `P`에만 비례 | 사건마다 조회 1회 + 탭마다 전송 1회. 묶어 보내기(예: 1초에 한 번)를 넣지 않으면 `E`에 비례해 늘어남 |
| **네트워크 요청 수** | 탭마다 시간당 `3600 / P`회의 HTTPS 요청이 CloudFront → Caddy → Tomcat 전 구간을 지나감. 매 요청마다 쿠키(JWT)와 헤더가 함께 감 | 연결은 탭마다 1개. 그 위로 `H`초마다 하트비트(주석 한 줄), 사건마다 이벤트 1개. 요청 헤더는 연결·재연결 때만 감 |
| **CloudFront** | 요청 수 = 폴링 횟수. 요금은 요청 수에 비례 | 요청 수 = 연결 수 + 재연결 수. 오리진 응답 제한 시간보다 짧은 `H`가 필요(가설, 설정 확인 필요) |
| **서버(Tomcat·메모리)** | 요청마다 스레드를 짧게 씀. 상태 없음 | 탭마다 소켓 1개 + `SseEmitter` 1개를 메모리에 유지. 대기 중에는 스레드를 잡지 않음(서블릿 비동기, 가설). 하트비트 전송용 스케줄러가 필요 |
| **지연** | 최악 `P`초, 평균 약 `P / 2`초. 자기 처리는 즉시 다시 조회해 반영 | 커밋 직후 전송(즉시). 연결이 끊긴 동안 생긴 사건은 재연결 때 받는 초기 건수로 맞춰짐 |
| **백그라운드 탭** | 브라우저가 숨겨진 탭의 타이머를 늦춤(외부 문서 기준, 확인 필요). 탭을 가리면 실제 주기가 `P`보다 길어짐 | 연결이 살아 있는 동안은 숨겨진 탭에도 이벤트가 도착함. 모바일 브라우저가 백그라운드로 가면 두 방식 모두 끊김 |
| **재배포·장애** | 영향 없음. 다음 폴링부터 정상 | 모든 연결이 끊기고 `EventSource`가 다시 연결함. 그때 `2 × T`회의 조회가 한꺼번에 발생 |
| **권한 변경 반영** | 요청마다 DB 역할을 확인하므로 다음 폴링에 반영 | 연결할 때만 확인. 로그아웃·탈퇴는 재연결 전까지 반영되지 않음. 다만 ADMIN 역할은 화면에서 바꿀 수 없어(`M003`) 회수 위험은 작음 |

정리하면 다음과 같습니다.
- **B**: DB·네트워크 부하가 "시간 × 열린 탭 수"에 비례하는 고정비입니다. 지연은 `P`가 결정합니다. 같은 `T`에서 `P`를 60초에서 10초로 줄이면 조회와 요청이 6배가 됩니다.
- **C**: 부하가 "사건 수"에 비례하는 변동비이고, 열린 연결을 유지하는 비용이 따로 듭니다. 지연은 짧지만 하트비트, 묶어 보내기, 재연결 처리, 운영 경로(CloudFront 제한 시간) 확인이 추가로 필요합니다.
- 지금 가정(`T`가 1~2개, 신청이 하루 몇 건)에서는 두 방식 모두 t4g.small과 db.t4g.micro에 의미 있는 부하를 주지 않을 것으로 예상됩니다(추정, 측정 전). 그래서 비교의 핵심은 자원보다 "즉시"를 만족하는지, 그리고 구현·운영 복잡도입니다.

### 권장 검토 (결정 아님)
ADR-003의 "최소 기능 후 리팩토링" 근거와 운영 경로 호환성(절대 제약)을 보면, 대안 B(폴링, 탭이 보일 때만, 처리 상태를 바꾸면 즉시 다시 조회)를 먼저 검토하는 것을 제안합니다. 건수 API는 C·D로 옮겨도 그대로 재사용됩니다(첫 연결 시 초기값). 목표 지연이 정해지고 폴링으로 부족하다고 확인되면 C(SSE)로 옮기는 것이 다음 단계 후보입니다.

## 5. 결정

- **선택한 대안:** 대안 C — SSE (사용자 결정 2026-10-26)
- **근거:** 목표 지연이 "즉시"다(사용자 결정 2026-10-26). SSE는 신청 저장이나 처리 상태 변경이 커밋되는 즉시 관리자 화면에 건수를 보낸다. 폴링(B)은 최악의 경우 폴링 주기만큼 늦고, 숨겨진 탭에서는 브라우저가 타이머를 늦춰 그보다 더 늦어질 수 있다. SSE는 새 의존성 없이 지금의 서블릿 스택(`SseEmitter`)과 같은 출처 쿠키 인증으로 만들 수 있다. 지금 규모(관리자 1명, 탭 몇 개)에서는 열린 연결을 유지하는 비용이 크지 않을 것으로 예상한다(추정, 측정 전).
- **다른 대안을 선택하지 않은 이유:**
  - A 들어올 때만 조회: 화면을 열어 둔 동안 새 신청이 반영되지 않는다.
  - B 폴링: 즉시 반영을 만족하지 못한다. 주기를 줄여 지연을 맞추면 요청과 DB 조회가 주기에 반비례해 늘어난다.
  - D 웹소켓: 지연은 C와 같지만 요구가 한 방향 전달뿐이다. 새 의존성과 보안 구성이 더 들어간다.
- **결정에 따르는 조건:** 아래는 4절 분석에서 나온 위험을 막기 위해 구현에 반드시 넣는다.
  1. 이벤트는 트랜잭션 커밋 뒤(`@TransactionalEventListener(AFTER_COMMIT)`)에 보낸다. 건수는 별도 조회로 다시 계산한다.
  2. 신청이 몰릴 때를 대비해 묶어 보내기(디바운스)를 넣어 전송 횟수에 상한을 둔다(ADR-003 근거 유지).
  3. CloudFront 오리진 응답 제한 시간보다 짧은 주기로 하트비트를 보낸다.
  4. 연결할 때 `validateAdmin`으로 권한을 확인하고 초기 건수를 바로 보낸다. 재연결 시 놓친 변경도 이 초기 건수로 맞춘다.
  5. 연결 중에는 DB 커넥션을 잡지 않는다(`open-in-view: false` 유지, 서비스 트랜잭션은 연결 수립 전에 끝냄).

## 6. 결과

### 기대 효과
- 새 신청이나 처리 상태 변경이 커밋되면 관리자 화면의 건수가 바로 바뀐다.
- 변화가 없을 때는 DB를 조회하지 않는다. 연결마다 하트비트만 오간다.
- 숨겨진 탭에서도 연결이 살아 있는 동안은 이벤트를 받는다.

### 감수하는 트레이드오프 / 위험
- 열린 탭마다 연결 1개와 `SseEmitter`를 메모리에 유지하고, 하트비트를 보낼 스케줄러를 운영한다.
- 운영 경로(CloudFront → Caddy)에서 SSE가 끊기지 않고 흐르는지 아직 확인하지 않았다(가설). 확인에 실패하면 설정 변경이나 대안 재검토가 필요하다.
- 연결 레지스트리가 메모리에 있다. 백엔드를 여러 대로 늘리면 인스턴스 간 전달(pub/sub)이 필요하다.
- 재배포 때 모든 연결이 끊기고 다시 연결된다. 권한은 연결할 때만 확인하므로, 로그아웃·탈퇴는 재연결 전까지 반영되지 않는다. ADMIN 역할은 화면에서 바꿀 수 없어(`M003`) 위험은 작다.
- 되돌리기 비용은 작다. 건수 조회 API는 폴링으로 돌아가도 그대로 쓰고, 바뀌는 것은 전달 계층뿐이다.

### 후속 작업
- FR-005의 "주기적으로 갱신"을 "변경이 생기면 즉시 반영"으로 고친다.
- 백엔드:
  - 건수 조회(`countByStatus(RECEIVED)`)
  - SSE 구독 엔드포인트(`/api/v1/admin/...`, `validateAdmin`)
  - 메모리 연결 레지스트리
  - 커밋 후 이벤트 리스너와 묶어 보내기
  - 하트비트 스케줄링(`@EnableScheduling` 또는 전용 스케줄러, 설정 추가는 사용자 확인)
- 프론트:
  - 관리자일 때 `EventSource`로 구독
  - 헤더 "관리자" 링크(모바일 메뉴 포함)와 상담 신청 메뉴에 배지
  - 로그아웃할 때와 관리자가 아닐 때는 구독하지 않음
- 운영:
  - CloudFront `/api/*` 동작의 오리진 응답 제한 시간 확인
  - Caddy의 SSE 전달 확인
  - 결과를 `docs/deploy-checklist.md`에 기록
- progress의 "권한 검사 DB 조회 검토" 항목과 연결 시점 권한 확인을 함께 정리한다.

## 7. 검증 계획

- 구현 전: 운영과 같은 경로(CloudFront → Caddy)에 최소 SSE 엔드포인트를 두고 두 가지를 측정한다. 하트비트 없이 몇 초 만에 끊기는지, 하트비트를 보내면 연결이 유지되는지. 이 결과로 하트비트 주기를 정한다.
- 테스트:
  - 구독: 관리자 200(`text/event-stream`), 직원·일반 회원 403, 비로그인 401
  - 연결하면 초기 건수가 오는지
  - 신청 저장 커밋 후 건수 이벤트가 오고, 롤백(필수 동의 누락 등)이면 오지 않는지
  - 처리 상태를 바꾸면 건수가 줄어드는지
  - 짧은 시간에 여러 건이 들어오면 묶어서 보내는지
- 로컬 QA: 다른 브라우저에서 신청하면 관리자 탭의 배지가 새로고침 없이 바뀌는지, 백엔드를 재시작한 뒤 자동으로 다시 연결되는지 확인한다.
- 운영: 실제 신청 후 배지 반영을 확인한다. 초기 몇 주 동안 연결 끊김과 재연결 빈도를 애플리케이션 로그로 관찰한다.

## 8. 재검토 조건

- 운영 경로 측정에서 SSE 연결을 안정적으로 유지할 수 없을 때. 이때는 폴링(B)이나 설정 변경을 다시 검토한다.
- 관리자·직원이 늘어 열린 연결이나 하트비트가 측정 가능한 부담이 될 때.
- 백엔드를 여러 대로 늘릴 때. 인스턴스 간 전달이 필요하다.
- 양방향 실시간 기능이나 다른 사이트 안 실시간 알림이 요구될 때. 웹소켓(D)이나 공용 이벤트 채널을 다시 검토한다.

## 9. 이력

- 2026-10-26 — Proposed — 초안 작성. ADR-003 대안 B의 전달 방식을 폴링, SSE, 웹소켓(과 들어올 때만 조회)으로 비교.
- 2026-10-26 — Proposed — 목표 지연을 "즉시"로 확정(사용자 결정). 1분 이내 폴링(B)과 SSE(C)의 DB·네트워크·서버 자원 비교 추가.
- 2026-10-26 — Accepted — 대안 C(SSE) 선택. 근거: 즉시 반영 필요. 커밋 후 전송, 묶어 보내기, 하트비트, 연결 시 권한 확인·초기 건수를 조건으로 기록.
