# 결정 사항

1. 관리자 정적 리소스 직접 수정 안건
    A안 — 현상 유지 (대표가 요청하면 개발자가 반영)
제
    장점
    - 추가 개발이 없어서 비용이 0이에요.
    - 모든 변경이 git 이력과 PR 리뷰를 거쳐요. 오타나 줄이 넘치는 문제를 배포 전에 걸러요.
    - 글귀가 코드 한 곳에만 있어서 어느 값이 화면에 나오는지 헷갈릴 일이 없어요.
    - 홈 화면이 지금처럼 정적 번들로 바로 그려져요. 깜빡임이 없어요.

    단점
    - 반영이 개발자 일정에 묶여요. 글귀 한 줄도 PR → 병합 → 자동 배포를 거쳐야 해요.
    - 대표가 바꿔 보고 마음에 안 들면 다시 요청해야 해서, 여러 번 시험해 보기가 불편해요.
    - 개발자가 없거나 바쁠 때 대응할 수 없어요.

    C안 — 히어로 전용 편집 화면 (관리자 화면에서 대표가 직접) (결정 및 구현 완료)

    장점
    - 대표가 원할 때 바로 바꾸고 바로 반영돼요.
    - 입력칸이 화면과 1:1(제목 1줄·목 2줄·설명)이에요. 미리보기가 있어서 비개발자도 헷갈리지 않아요.
    - 코드에 있는 기본 문구로 언제든 되돌릴 수 있어서, 잘못 고쳐도 복구가 쉬워요.
    - 저장 대상이 한 건이라 DB 전체 관리(D안)보다 훨씬 작아요. 관리자 화면과 권한 검사는 이미 있어요.

    단점
    - 개발 작업이 필요해요: 저장·조회 API, DB 테이블 1개, 관리자 편집 화면, 홈에서 저장값 읽기. 운영 DB에 DDL도 적용해야 해요.
    - 홈을 열 때 글귀 조회 요청이 1번 늘어요. 기본 글귀가 보였다가 저장 글귀로 바뀌는 깜빡임을 막는 처리가 필요해요.
    - 글귀가 코드(기본값)와 DB(저장값) 두 곳에 있게 돼요. 개발자가 기본값을 고쳐도 저장값이 있으면 화면에 안 나와서 헷갈릴 수 있어요.
    - 변경 이력이 git에 남지 않아요. 이전 문구를 보관할지 따로 정
    - 히어로 외 문구까지 넓히려면 항목마다 편집 화면을 또 만들어야 해요.

    회의에서 정하면 좋은 것

    1. 얼마나 자주 바꾸고 싶은지: 한 달에 한 번도 안 될 것 같으면 A안으로 충분하고, 계절·행사마다 바꾸고 싶으면 C안이 맞아요.
    2. 히어로 글귀의 범위: 제목 두 줄과 설명만인지, 운영 지역 줄(용인 · 수원 · …)도 포함하는지
